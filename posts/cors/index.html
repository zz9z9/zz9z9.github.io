WEB - CORS(Cross-Origin Resource Sharing) 살펴보기

Lee JaeYoon Nov 14 2026-11-14T22:00:00+09:00
Nov 15 2026-11-15T01:47:53+09:00 32 min

1. 정의

CORS는 서버가 응답 헤더로 “다른 출처(origin)와 이 응답을 공유해도 된다”고 밝히는 HTTP 위의 프로토콜이다. (참고 : Fetch 표준)

  • Cross-Origin : 출처가 다른
  • Resource : URL로 요청하는 모든 자원 (응답 본문이 없는 경우도 포함)
  • Sharing : 공유할지

현재 페이지와 요청 URL의 {scheme}://{host}:{port}가 모두 같을 때 ‘동일한 출처’로 본다.

2. 목적

SOP(Same-Origin Policy) 때문에 브라우저가 출처가 다른 서버의 응답을 읽을 수 없던 제약을 서버가 허락한 경우에 한해 안전하게 풀어 주기 위함이다.

  • 브라우저는 SOP 제약 때문에 출처가 다른 서버의 응답을 읽을 수 없었다.
  • 웹 서비스가 발전하면서 이 제약을 풀어야 하는 상황이 생겼다.
  • 그래서 SOP 제약을 안전하게 허용하는 방법으로 CORS가 등장했다.

3. 배경

SOP 제약이 도입된 이유와, 없을 때의 악용 예시

  • JS가 도입되면서 페이지 안에서 응답을 프로그래밍적으로 다룰 수 있게 됐고, 그만큼 악용 범위도 넓어졌다.
  • 브라우저는 요청에 사용자의 쿠키를 자동으로 붙이고, 사용자 기기의 네트워크 위치에서 요청을 보낸다.
  • SOP가 없으면 아무 사이트의 JS나 사용자 브라우저를 빌려
    • 사용자 자격으로 로그인된 응답(개인 데이터)을 읽거나
    • 공격자는 직접 닿을 수 없고 사용자 기기에서만 닿는 곳(사내망, 공유기·IoT, localhost 등)의 응답을 읽어 외부로 보낼 수 있다.

CORS : 나중엔 왜 제약을 벗어나야 했을까?

  • 막아야 하는 정보도 있지만, 모두에게 공개하고 싶은 정보도 있다. (예: 기상 데이터)
  • 허용한 특정 출처에서만 쓰게 하고 싶은 경우도 있다. (예: 계약한 파트너에게만 시세 제공)
  • 표준이 없어서 JSONP 같은 위험한 우회책이 쓰였고, CORS는 이를 안전한 정식 경로로 대체했다.
참고 : JSONP 우회 방식

1

응답을 “읽은” 게 아니라 “실행”한 것이라 SOP에 걸리지 않는다.

위험한 이유

문제설명
제공자를 완전히 믿어야 함응답이 데이터가 아니라 실행되는 코드다. 서버가 해킹되면 임의 코드가 a.com 페이지에서 실행된다
허락 대상을 고를 수 없음<script> GET 요청엔 Origin 헤더가 없어 누가 불렀는지 알기 어렵다 → 아무 사이트나 호출 가능

기능 제약GET만 가능, 헤더 지정 불가, 상태 코드 기반 에러 처리가 어려움

왜 서버의 허락이 필요했을까?

  • 이 자원을 어디서 써도 되는지는 자원을 가진 서버만 안다. 그래서 서버가 결정하고 브라우저가 집행한다.
  • 기본값이 거부인 opt-in 방식이다.
    • CORS를 모르는 서버는 ‘허락해야 한다’는 사실조차 모른다. 관련 헤더가 없으면 허락하지 않은 것으로 본다.
    • 덕분에 기존 서버는 아무것도 바꾸지 않아도 안전하다.
    • 쿠키가 실린 응답은 한 번 더 허락이 필요하다. (ACAC: true + origin 명시)

4. 동작 방식

서버는 응답 헤더로 허락하고, 브라우저는 그 헤더를 보고 응답을 JS에 넘길지 판별한다.

           OPTIONS /orders

           Access-Control-Request-Method: PUT

           Access-Control-Allow-Origin: https://a.com

           Access-Control-Allow-Credentials: true
   ▼
[브라우저] 허락 확인
   ├─ 통과 → 본 요청 전송 → 이후는 단순 요청과 같은 흐름
   └─ 실패 → 본 요청을 아예 보내지 않음
  • 이 사전 요청을 preflight 요청이라 한다. (표준 명칭 : CORS-preflight request)
    • OPTIONS 메서드로 Access-Control-Request-Method · Access-Control-Request-Headers를 실어 보내며, 쿠키 없이 보낸다.
  • 단순 요청은 서버가 이미 처리한 뒤 읽기만 막고, preflight 대상은 본 요청 자체를 막는다.
Preflight 요청이 필요한 이유
  • CORS 이전에는 다른 origin으로 보낼 수 있는 요청이 <form>이 보낼 수 있는 범위로 한정되어 있었다.
    • 예) JSON 본문의 POST, PUT · DELETE, 커스텀 헤더가 붙은 요청은 다른 origin에서 올 수 없었다.
  • 그래서 서버도 이런 요청이 다른 출처에서 오리라 생각하지 않고 별다른 검증을 하지 않을 수 있다.
  • CORS가 등장하면서 JS(fetch, XHR. axios · jQuery $.ajax 같은 라이브러리도 내부적으로 이 둘을 쓴다)로 이런 요청도 다른 origin에 보낼 수 있게 됐다.
    • 그런데 이런 요청을 바로 보내면, 위처럼 다른 출처의 요청을 가정하지 않은 서버에서는 악의적인 요청이 그대로 처리될 수 있다.
    • 그래서 브라우저는 본 요청 전에 사전 요청을 보내고, 응답의 ACAO · ACAC · Access-Control-Allow-Methods · Access-Control-Allow-Headers를 검증해 본 요청을 보내도 되는지 확인한다.
    • CORS 처리가 되어 있지 않은 서버는 ACAO를 응답하지 않으므로, 브라우저가 본 요청을 내보내지 않는다.
    • 즉 단순 요청은 보내는 것 자체는 서버 허락과 무관하고 응답 읽기만 허락에 달려 있지만, preflight 대상 요청은 보내는 것 자체가 서버의 허락에 달려 있다.
  • 반대로 <form>으로도 보낼 수 있던 범위의 요청(단순 요청)은 새로운 위험이 아니므로 preflight 없이 바로 보낸다.
Preflight 요청이 발생하는 상황

요청 대상 · 모드가 오른쪽이고, 나머지 세 조건(메서드 · 헤더 · Content-Type) 중 하나라도 오른쪽이면 preflight(OPTIONS)를 먼저 보낸다. 그 외에는 preflight 없이 바로 전송한다.

요청 대상 · 모드는 아래 “모든 요청이 검사 대상은 아니다” 참고

구분preflight 없음preflight 대상
요청 대상 · 모드same-origin 요청, 또는 navigate · no-cors 모드cross-origin + cors 모드 (fetch, XHR 등)
메서드GET, HEAD, POSTPUT, DELETE, PATCH 등
헤더CORS-safelisted 헤더만 (Accept, Accept-Language, Content-Language, Content-Type(아래 3종), Range)Authorization, X-Requested-With 같은 커스텀 헤더 추가
Content-Typeapplication/x-www-form-urlencoded, multipart/form-data, text/plain (또는 body 없음)application/json 등 그 외

same-origin이면 JSON PUT이어도 preflight가 없고, navigate · no-cors는 애초에 단순한 메서드 · 헤더만 보낼 수 있다.

  • 메서드 · 헤더 · Content-Type이 모두 왼쪽인 요청을 단순 요청이라 부른다.

모든 요청이 검사 대상은 아니다

CORS의 목적은 허락받지 않은 출처의 JS가 응답을 읽어 악용하는 것을 막는 것이다.
따라서 cross-origin 응답이라도 그 응답이 페이지의 JS에 넘어가지 않는 요청이면 검사할 필요가 없다.
cross-origin이면서 cors 모드인 요청만 검사한다.

검사 대상이 아닌 요청의 응답에도 서버가 ACAO · ACAC를 붙일 수 있다. (nginx 일괄 설정, Origin이 실린 <form> POST 등) 브라우저가 보지 않으므로 효과는 없다.

cross-origin 요청

출처 관계

요청을 시작한 문서와 요청 URL의 관계는 브라우저가 요청 헤더 Sec-Fetch-Site로 알려 준다. 값은 아래 넷 중 가장 좁은 하나로 정해진다.

cross-origin은 표의 same-site 또는 cross-site인 경우다.

관계기준예시 (https://app.example.com 기준)Sec-Fetch-SiteCORS (origin 기준)
same-originscheme · host · port 모두 같음https://app.example.com/api/orderssame-origin검사 없음
same-site (origin은 다름)origin은 다르지만 scheme · eTLD+1이 같음https://foo.example.com, https://app.example.com:8443same-site검사 대상
cross-siteeTLD+1 또는 scheme이 다름https://evil.com, http://app.example.comcross-site검사 대상
none시작한 문서가 없음주소창 입력, 북마크none해당 없음
  • 포함 관계로 보면 same-origin ⊂ same-site다.
    • scheme · host가 같으면 eTLD+1도 같으니 same-origin 요청은 당연히 same-site다.
    • 다만 Sec-Fetch-Site는 더 좁은 same-origin으로 표시하므로, 표의 same-site 행은 “same-site이면서 origin은 다른” 경우만 뜻한다.
  • CORS는 origin을, SameSite는 site를 기준으로 하므로 같은 요청이 “CORS로는 cross-origin, SameSite로는 same-site”일 수 있다. 형제 서브도메인이 이 경우다.
  • scheme이 다르면 eTLD+1이 같아도 cross-site다. (schemeful same-site)
요청 모드

요청 모드(request mode)는 Fetch 표준이 정의한 요청 객체의 속성 중 하나로, 목적지가 cross-origin일 때 브라우저가 이 요청을 어떻게 다룰지 정한 규칙이다.
보낼지 말지, 서버의 CORS 허락을 확인할지, 응답 내용을 JS에 보여 줄지가 이 값으로 갈린다.
요청을 만드는 쪽(fetch(), HTML의 <img> 등)이 요청을 시작할 때 이 조건을 정해 둔다.
브라우저는 이 값을 Sec-Fetch-Mode 요청 헤더에 그대로 담아 서버에 알린다.

모드와 목적지는 따로 정해진다

값정하는 쪽정해지는 시점

  • 표준에서 요청 모드의 초기값은 no-cors다. HTML의 <img>, 일반 <script>처럼 모드를 따로 지정하지 않는 요청이 이 값으로 나간다.
  • fetch()와 XHR은 API가 모드를 cors로 지정해서 보내므로, 이 둘의 기본값은 cors다.

불투명(opaque) 응답

Response.type === 'opaque'인 응답이다. status는 0, 헤더는 비어 있고, body는 null이다.
브라우저는 이 응답을 쓰기만 하고 JS에 내용을 보여 주지 않는다. 예를 들어 <img> 렌더링이나 Service Worker 캐시 저장에는 쓰이지만, JS는 요청이 성공했는지조차 알 수 없다.

5. Access-Control-Allow-Origin, Access-Control-Allow-Credentials

서버가 허락을 담아 보내는 응답 헤더는 Access-Control-Allow-Origin(ACAO), Access-Control-Allow-Credentials(ACAC) 두 개이고, 브라우저는 이 두 값을 보고 응답을 JS에 넘길지 판별한다.

Access-Control-Allow-Origin (ACAO)

  • 서버가 “이 origin의 JS에는 응답을 보여 줘도 된다”고 허락한 origin이다.
  • 목록이 아니라 값 하나다. 정확한 origin 하나, *, null 중 하나가 들어간다.
    • 값이 여러 개이거나 헤더가 2개면 브라우저가 거부한다.
  • 서버는 허용 목록을 들고 있다가 요청 Origin과 일치하는 것 하나를 그대로 돌려준다(echo). Spring도 이렇게 동작한다.
  • 브라우저는 이 값이 현재 페이지의 origin과 같으면(또는 *면) 응답을 JS에 전달한다.

Access-Control-Allow-Credentials (ACAC)

  • Fetch 표준의 자격 증명(credentials)은 쿠키, TLS 클라이언트 인증서, 브라우저가 관리하는 HTTP 인증(Basic 등) 세 가지다.
    • JS가 직접 넣는 Authorization 헤더는 여기에 해당하지 않는다. 커스텀 헤더라서 preflight 대상이 될 뿐이다.
  • 요청이 자격 증명을 실을 수 있는지는 요청의 credentials 모드가 정한다.
credentials 모드자격 증명 첨부지정 방법
omit항상 안 실음fetch(url, {credentials: 'omit'})
same-originsame-origin 요청에만 실음fetch() 기본값, XHR 기본값
includecross-origin 요청에도 실음fetch(url, {credentials: 'include'}), xhr.withCredentials = true
  • cross-origin 요청의 모드가 include이면 ACAO가 허용된 출처여도 ACAC가 true여야 응답을 JS에 전달한다.
  • 기준은 자격 증명이 실제로 실렸는지가 아니라 모드다.
    • 모드가 include이면 아래 제약이 적용된다. (Fetch 표준의 CORS check는 credentials mode만 본다)
credentials 모드가 include일 때의 제약
  • ACAO에 *를 쓸 수 없고 정확한 origin이어야 한다.
    • * + 쿠키를 허용하면 아무 사이트의 JS나 로그인된 응답(개인 정보)을 읽게 되어 SOP가 없는 것과 같아진다.
    • 그래서 쿠키가 실린 응답은 서버가 믿는 출처를 명시해 의식적으로 허락하도록 강제한다.
    • 단, 서버가 요청 Origin을 검사 없이 그대로 돌려주면 결과는 *와 같으므로, 허용 목록과 일치할 때만 돌려줘야 한다.
  • ACAC가 true여야 한다.
  • Access-Control-Allow-Methods · Access-Control-Allow-Headers에도 *를 쓸 수 없다.

두 헤더의 관계 : ACAO가 ‘인증’, ACAC가 ‘인가’인 것은 아니다

둘 다 origin에 대한 허락이고 사용자와는 무관하다.

  • ACAO : “이 origin에 응답을 보여 줘도 된다”
  • ACAC : “자격 증명이 실린 응답도 보여 줘도 된다”

열쇠 두 개가 모두 있어야 열리는 구조다.

6. 서버도 Origin을 검사한다 : Spring Web MVC 기준

CORS 표준은 브라우저만 검사하지만, Spring은 서버에서도 Origin을 검사해서 허용되지 않은 Origin이면 컨트롤러를 실행하지 않고 403으로 거부한다.
브라우저 검사를 대체하는 것은 아니고, 아래 단계를 순서대로 통과한 요청에만 적용된다.

검사 흐름
단계조건해당하지 않으면
1. DispatcherServlet 도달앞단 서블릿 필터가 응답을 끝내지 않음CORS 처리 없음 (헤더도 안 붙음)
2. 설정 매칭요청 경로에 맞는 설정이 있음 (addMapping 경로, @CrossOrigin)본 요청은 그대로 통과, preflight는 403
3. CORS 요청인가Origin이 있고, 서버가 보는 자기 scheme · host · port와 다름 (CorsUtils.isCorsRequest)검사 없이 통과 (Vary만 붙음)
4. ACAO 미설정앞단(CorsFilter, Security http.cors(), 직접 만든 필터 등)이 이미 ACAO를 붙이지 않음중복 방지를 위해 건너뜀
5-a. preflightOrigin · 메서드 · 헤더 검사허용이면 컨트롤러 없이 200 + Access-Control-Allow-*, 아니면 403
5-b. 본 요청Origin · 메서드 검사허용이면 ACAO/ACAC를 붙이고 컨트롤러 실행, 아니면 403 Invalid CORS request (컨트롤러 실행 안 됨)
  • 5-b의 403은 CORS 표준이 요구하는 동작이 아니라 Spring의 구현이다.
    • 허용 안 된 Origin의 단순 요청도 서버 단에서 막히는 효과가 있지만, 1~3단계에서 빠지는 요청은 이 검사를 거치지 않는다.
  • 4단계의 “앞단”은 같은 WAS 안에서 먼저 실행되는 필터 · 인터셉터다.
    • nginx 같은 외부 프록시가 붙이는 헤더는 Spring이 볼 수 없어서, 둘 다 붙이면 ACAO가 2개가 되어 브라우저가 거부한다.
  • 브라우저의 CORS는 응답 읽기만 막는다. 요청은 이미 서버에 도착해 처리되고, 상태 변경도 일어날 수 있다.
  • 반면 서버가 403으로 거부하면 요청 처리 자체가 막힌다. 결과적으로 Origin 검사 방식의 CSRF 방어 효과가 생긴다.
