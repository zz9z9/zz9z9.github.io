# 2. 과제 설명
- 과제 조건에 **실무에서 사용**한다고 가정 및 사용자는 영업사원이라고 했기 때문에, 어드민성(운영자용) 애플리케이션이라고 생각하고 만듦

## 아키텍처
- 웹 애플리케이션에서 보편적으로 사용되는 계층형 구조 (프레젠테이션 레이어 - 서비스 레이어 - 데이터 레이어)를 사용했습니다.

## 코드 작성시 생각한 부분
- 개인적으로 유지보수하기 좋은 코드는 예측이 쉬운 코드라고 생각
- 예측이 쉬우려면,
  - 기존 코드를 변경했을 때 영향범위가 크면 안됨
  - 코드를 봤을때 대략 어떤 역할을 하는 코드겠다를 알 수 있어야됨

- 그래서, 코드를 작성할 때
  - 하나의 객체에 너무 많은 책임이 가지 않는 것
  - 레이어별 관심사가 적절히 분리되는 것

## 구현시 고민한 부분
### 동시성 처리
- 크게 두 가지 부분에 대한 동시성 처리 필요하다고 생각.
1. 같은 고객에 대해 수정/삭제
2. 같은 이메일로 변경되는 상황인 경우

- 따로 요구사항이 없었기 때문에 나름의 정책
  - '고객 정보 변경'이라는 요청의 특성을 고려했을때, 동시에 접근한 것 중 하나만 처리에 성공하고 나머지는 실패 알림을 통해 '아 이미 해당 고객에 대해 처리중이구나'라는 것을 사용자들이 인지할 수 있도록 하는 것이 나을 것으로 판단
  - 또한, 이미 처리되고 있는 액션이 수정인지 삭제인지 등에 대해 구체적으로 알릴 수 있도록 구현

- 만약 사용자가 고객 a, b, c, d를 삭제하려는 상황에서 고객 d가 이미 변경 처리되고 있는 경우, 나머지 a, b, c는 삭제가 가능하게 해야 할지에 대해 고민했지만, 이런 경우가 빈번하지는 않을 것으로 생각했고 왜 d는 삭제되지 않았는지에 대해 사용자가 헷갈릴 수 있으므로 이러한 케이스도 실패로 처리하였습니다.

**구현**
- 동시성을 제어하는 코드가 필요한 부분에 반복해서 나타나는 것이 코드의 가독성도 떨어뜨리고 중복 코드 작성이라는 생각이 들었음
- 그리고 특정 레이어의 관심사가 아닌 공통 관심사라고 생각 이를 해결하기 위해 AOP를 활용
- Lock을 잡는 컨셉, 근데 허점이 있음

### 기타
- 요구사항에 맞춰서 구현하려고 함
- 헷갈렸던건 contactNum : contactNum을 식별자라고 생각해서 변경하지 못하도록

### 미흡
- 양방향 like 이런걸 서비스 레이어에서 처리해야한다고 생각했는데, 되돌아보니 repository쪽에 구현하는게 더 맞는 설계였던것 같음
- 또한, 동시성 처리에서 미흡한 부분들이 있음
