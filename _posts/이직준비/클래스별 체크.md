- [x] **DataFormatValidator**
> `EMAIL_REGEX = "^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+$";`
> `CELL_PHONE_REGEX = "^010(-\\d{3}-\\d{4}|-\\d{4}-\\d{4}|\\d{7,8})$";`

- `^` : 문장 시작
- `$` : 문장 끝
- `[]` : 문자셋, 괄호안의 어떤 문자든
- `()` - 그룹: 특정 부분을 하나의 단위로 묶는 것
- `+` : 하나 이상
  - 따라서, `[A-Za-z0-9+_.-]+` 이거는 대문자, 소문자, 숫자 `+_.-` 문자 중 하나 이상이면됨
- `\d` : 숫자

- 이메일 개선해보기
  - `"^[a-z0-9]+([._-][a-z0-9])*@[a-z]+\\.[a-z]{2,}$"`
  - `"^([a-z0-9]+([._-][a-z0-9])*){5,10}@[a-z]+\\.(com|org|net)$";
`
  - 이메일 소문자만 가능
  - 아이디는 5자 ~ 20자 사이
  - 특정 도메인만 가능 (`.com`, `.org` 등등)

  - PATCH는 부분 수정 및 멱등성 보장할 수도 안할수도 있음, PUT은 전체수정 및 멱등성 보장이라는 관점에서 봤을때 `PATCH`가 더 적합했을 것 같음

  - RESTful 관점에서는 DELETE 요청에서는 @RequestBody 없이 리소스를 URI로 식별하는 것이 일반적. DELETE에서는 보통 리소스를 URI로 직접 표현하는 것이 RESTful 원칙에 더 부합
  - 일부 API 클라이언트 (예: 브라우저)에서 DELETE 메서드는 Request Body를 허용하지 않음
  - DELETE 요청에서 쿼리 스트링을 활용하는 방식으로 변경 가능
- ResponseEntity
  - 개인적으로 느끼기에 가장 큰 장점은 HttpServletResponse를 직접 조작하지 않고, 간결하게 http 응답을 제어할 수 있다는 것
  - 즉, API 설계에서 보다 세밀한 HTTP 응답 제어가 가능하다. (HTTP 응답 코드와 헤더를 명시적으로 설정할 수 있다.)
    - ResponseEntity.ok()를 사용하면 응답 코드가 200(OK)로 설정되지만, 필요하면 ResponseEntity.status(HttpStatus.BAD_REQUEST).body(...)처럼 다른 상태 코드도 설정할 수 있다.

- `RuntimeException`을 상속하는 이유?
  - Checked Exception의 경우 예외 처리를 강제하는 이유
    - 해당 예외를 발생시킬 수 있는 여지를 포함하고 있는 메서드를 호출하는 호출자가 예외에 대해 인지하고 적절하게 처리하도록 할 수 있게 하기 위해.
      - 이 때문에, 모든 호출자에서 throws를 선언해야 하므로, 코드가 지나치게 복잡해짐.
	  - 비즈니스 로직에서 Checked Exception을 남발하면, 예외 처리가 불편해짐. try-catch를 여기저기 추가해야 해서 코드 가독성이 나빠질 수 있음.
    - 하지만, `ClientModificationNotAllowedException`은 뭔가 catch해서 재처리하거나 하는 등의 액션을 강제할 필요가 없음
  - Unchecked Excpetion의 경우는 예외 처리를 강제하지 않았을까?
    - RuntimeException은 프로그램의 어디에서나 발생할 수 있으며 매우 다양한 경우가 있다.
    - 만약, 모든 메서드 선언에 이러한 예외를 추가해야 하면 프로그램의 명확성이 떨어진다.
    - 예를 들어, 배열을 사용하는 메서드에서 `ArrayIndexOutOfBoundException`, 객체 참조하는 코드가 있는 곳에서 NullPointerException 일일이 처리해줘야한다면 코드가 매우 지저분해질 것이다.
    - throws를 선언하지 않아도 되므로 호출하는 모든 코드에서 예외 처리를 강제하지 않아도 됨. 따라서, 비즈니스 로직에서 **필요할 때만 예외를 잡을 수 있음.**
    -  GlobalExceptionHandler에서 @ExceptionHandler를 통해 쉽게 처리 가능.
  - Throwable은 시스템 오류(Error)까지 포함하므로 비즈니스 로직에서 발생하는 예외를 표현하는 데 부적절함. 또한 catch (Exception ex)에서 잡히지 않음!
