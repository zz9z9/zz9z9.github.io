## synchronized
- 동기화(Synchronization)**는 내부적으로 **intrinsic lock(내재적 락) 또는 monitor lock(모니터 락)**으로 알려진 내부 엔터티(entity)를 중심으로 구축된다.
  - 이는 간단히 **"모니터(monitor)"**라고도 불린다.

-  Intrinsic Lock = Monitor Lock = Object Lock
  - Java의 모든 객체는 **하나의 내재적 락(intrinsic lock, monitor lock)**을 가지고 있음.
  - synchronized 키워드를 사용하면 자동으로 해당 객체의 intrinsic lock을 획득 및 해제.
  - 재진입 가능(Reentrant Lock) → 같은 스레드가 동일한 락을 여러 번 획득할 수 있음.

- Intrinsic lock의 두 가지 역할
  - 객체의 상태에 대한 배타적(독점적) 접근을 강제하는 것
    - 즉, 한 번에 하나의 스레드만 해당 객체의 동기화된 영역(메서드나 특정 코드 블록)을 실행할 수 있음.
  - 가시성(visibility)에 필수적인 happens-before 관계를 설정하는 것
    - happens-before 관계 : **Java 메모리 모델(Java Memory Model, JMM)**에서 한 작업의 결과가 다른 작업에서 반드시 보이도록 보장하는 관계를 의미

```java
class SharedResource {
    private int value = 0;

    public synchronized void increment() { // 락 획득
        value++;  // 메모리 수정
    } // 락 해제 (happens-before 관계 형성)

    public synchronized int getValue() { // 같은 락 획득
        return value; // 이전 변경 사항을 반드시 볼 수 있음
    }
}
```

- 위 코드에서 increment()가 value를 변경하고 락을 해제하면, 이후 getValue()가 같은 락을 얻었을 때 value의 변경된 값을 항상 보장받을 수 있어. 이게 happens-before 관계야.
- "한 스레드가 intrinsic lock(내재 락)을 소유하는 동안, 다른 스레드는 동일한 락을 획득할 수 없다. 다른 스레드가 해당 락을 획득하려고 시도하면, 블록(block) 상태가 된다.
- "스레드가 synchronized 메서드를 호출하면, 해당 메서드가 속한 객체의 intrinsic lock을 자동으로 획득하며, 메서드가 반환될 때 자동으로 해제된다. 이 락 해제는 예외가 발생하여 메서드가 비정상적으로 종료되더라도 반드시 수행된다."

### 공정성 ?
> 어떤 스레드가 우선적으로 락을 얻을 수 있는지를 결정하는 정책

- 기본적으로, 락(synchronized, ReentrantLock)은 공정하지 않은 방식(비공정, unfair)으로 동작합니다.
- 즉, 락이 해제되었을 때 어떤 스레드가 락을 획득할지는 랜덤이며, 먼저 요청한 스레드가 항상 먼저 락을 얻는 것은 아닙니다.
- **공정한 락(fair lock)**을 설정하면 오래 기다린 스레드가 먼저 락을 획득하도록 보장할 수 있습니다
- synchronized 블록을 빠져나온 순간, 어떤 스레드가 다음으로 락을 획득할지는 JVM이 내부적으로 결정합니다.

### 모니터란 ?
> Monitor = Lock + Wait-Notify

- Monitor는 intrinsic lock을 제어하는 내부 시스템 구조.
- synchronized 키워드는 Monitor를 통해 락을 관리.
- Monitor는 wait(), notify(), n*otifyAll()을 지원하여 스레드 간 협력(synchronization)을 제공.
- 동작 방식
```java
synchronized (lock) {
    while (!condition) {
        lock.wait(); // 🔹 락을 해제하고 기다림 (락을 해제하고 대기 (다른 스레드가 notify() 호출할 때까지))
    }
    // 🔹 조건 충족되면 실행
}
```

### Mutex(뮤텍스)란?
- **Mutual Exclusion(상호 배제)**의 줄임말.
- 한 번에 하나의 스레드만 접근 가능.
- Binary Semaphore(0 또는 1)와 유사 → 0이면 접근 불가, 1이면 접근 가능.
- 예시 : ReentrantLock 활용

```java
import java.util.concurrent.locks.ReentrantLock;

class SharedResource {
    private final ReentrantLock lock = new ReentrantLock();

    public void access() {
        lock.lock();
        try {
            System.out.println(Thread.currentThread().getName() + " is accessing...");
        } finally {
            lock.unlock();
        }
    }
}
```

### Semaphore(세마포어)란?
- N개의 스레드가 동시에 접근 가능하도록 허용.
- 리소스 개수 제한을 두는 경우 사용.
- Semaphore(N) → 최대 N개의 스레드가 접근 가능.

```java
import java.util.concurrent.Semaphore;

class SharedResource {
    private final Semaphore semaphore = new Semaphore(2); // 최대 2개 스레드 허용

    public void access() {
        try {
            semaphore.acquire(); // 🔹 접근 허용 요청
            System.out.println(Thread.currentThread().getName() + " is accessing...");
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            semaphore.release(); // 🔹 사용 종료 후 해제
        }
    }
}
```

| 개념 | `synchronized` | **Mutex (뮤텍스)** | **Semaphore (세마포어)** |
| --- | --- | --- | --- |
| **설명** | Java의 기본 동기화 방식 | 하나의 스레드만 접근 가능 | N개의 스레드가 접근 가능 |
| **락 개수** | **객체당 1개** (Intrinsic Lock) | **1개** (Binary Lock) | **N개** (Permit 개수 조절 가능) |
| **동시 접근 가능 여부** | ❌ 불가능 (단일 스레드) | ❌ 불가능 (단일 스레드) | ✅ 가능 (여러 개의 스레드) |
| **Happens-Before 보장** | ✅ O | ✅ O | ❌ X |
| **wait/notify 지원** | ✅ O (`wait()`, `notify()`) | ❌ X | ❌ X |
| **사용 목적** | **객체 단위 락 관리** | **스레드 간 락 관리** | **리소스 개수 제한** |


### "객체 단위 락 관리" vs "스레드 간 락 관리"
- 객체 단위 : A라는 객체, B라는 객체 각각이 락을 가짐
- 스레드 단위 : A,B 모두 동일한 락을 가질 수 있음 (즉 다른 객체라도 같은 락 적용 가능)


## ReentrantLock

> "Reentrant(재진입 가능)"한 락이기 때문에, 같은 스레드가 동일한 락을 여러 번 획득할 수 있도록 허용하는 특징이 있음.

**재진입 ?**

> 동일한 스레드가 같은 락을 여러 번 획득할 수 있도록 보장하는 기능

- synchronized 키워드도 기본적으로 재진입이 가능함.
- 한 스레드가 lock.lock()을 호출하여 락을 획득한 후, 같은 스레드에서 다시 lock.lock()을 호출해도 블로킹되지 않고 정상 실행됨.
- 단, lock.lock()을 여러 번 호출했다면, 해당 횟수만큼 unlock()을 호출해야 락이 완전히 해제됨.

- unlock을 통해 원하는 시점에 락을 해제할 수 있음 (즉, 락을 좀 더 세밀하게 컨트롤 가능)
  - 대신, 제대로 release 안하면 계속 락 잡혀있을 수 있음
- synchronized는 블록이 끝날 때까지 무조건 대기하지만, ReentrantLock은 tryLock()을 사용하여 대기 없이 바로 락을 시도할 수 있음.
  - 또는 tryLock(2, TimeUnit.SECONDS) 이런식으로 일정 시간 동안만 기다릴 수도 있음

```java
import java.util.concurrent.locks.ReentrantLock;

public class ReentrantLockExample {
    private final ReentrantLock lock = new ReentrantLock();

    public void outerMethod() {
        lock.lock();  // :closed_lock_with_key: 첫 번째 락 획득
        try {
            System.out.println(Thread.currentThread().getName() + " - Entering outerMethod()");
            innerMethod(); // :rocket: 내부 메서드 호출
        } finally {
            lock.unlock();  // :unlock: 첫 번째 락 해제
        }
    }

    public void innerMethod() {
        lock.lock();  // :closed_lock_with_key: 같은 락을 다시 획득 (재진입)
        try {
            System.out.println(Thread.currentThread().getName() + " - Entering innerMethod()");
        } finally {
            lock.unlock();  // :unlock: 두 번째 락 해제
        }
    }

    public static void main(String[] args) {
        ReentrantLockExample example = new ReentrantLockExample();
        Thread t1 = new Thread(example::outerMethod, "Thread-1");

        t1.start();
    }
}
```

## ReentrantLock 파헤치기

```java
@ReservedStackAccess
final void lock() {
    if (!initialTryLock())
        acquire(1);
}

@ReservedStackAccess
final boolean tryLock() {
  Thread current = Thread.currentThread();
  int c = getState();
  if (c == 0) {
    if (compareAndSetState(0, 1)) {
      setExclusiveOwnerThread(current);
      return true;
    }
  } else if (getExclusiveOwnerThread() == current) {
    if (++c < 0) // overflow
      throw new Error("Maximum lock count exceeded");
    setState(c);
    return true;
  }
  return false;
}

static final class NonfairSync extends Sync {
  private static final long serialVersionUID = 7316153563782823691L;

  final boolean initialTryLock() {
    Thread current = Thread.currentThread();
    if (compareAndSetState(0, 1)) { // first attempt is unguarded
      setExclusiveOwnerThread(current);
      return true;
    } else if (getExclusiveOwnerThread() == current) {
      int c = getState() + 1;
      if (c < 0) // overflow
        throw new Error("Maximum lock count exceeded");
      setState(c);
      return true;
    } else
      return false;
  }

  /**
   * Acquire for non-reentrant cases after initialTryLock prescreen
   */
  protected final boolean tryAcquire(int acquires) {
    if (getState() == 0 && compareAndSetState(0, acquires)) {
      setExclusiveOwnerThread(Thread.currentThread());
      return true;
    }
    return false;
  }
}
```

private static final Unsafe U = Unsafe.getUnsafe();

    return U.compareAndSetInt(this, STATE, expect, update);

### 동작 방식
> ReentrantLock은 AbstractQueuedSynchronizer(AQS)를 기반으로 동작하며, state 필드를 사용하여 락의 상태를 관리

```java
final void lock() {
    if (!initialTryLock())  // 1. 먼저 한 번 락을 시도
        acquire(1);         // 2. 실패하면 큐에 추가되고 블록됨
}

final boolean initialTryLock() {
  Thread current = Thread.currentThread();
  if (compareAndSetState(0, 1)) {  // CAS를 이용해 state를 0에서 1로 변경 (락 획득)
    setExclusiveOwnerThread(current);
    return true;
  } else if (getExclusiveOwnerThread() == current) {  // 현재 스레드가 이미 락을 소유 중인가?
    int c = getState() + 1;  // 재진입이면 state 증가
    if (c < 0) throw new Error("Maximum lock count exceeded");
    setState(c);
    return true;
  } else
    return false;
}

final boolean tryLock() {
  Thread current = Thread.currentThread();
  int c = getState();
  if (c == 0) {
    if (compareAndSetState(0, 1)) {
      setExclusiveOwnerThread(current);
      return true;
    }
  } else if (getExclusiveOwnerThread() == current) {  // 이미 락을 가지고 있으면
    if (++c < 0) throw new Error("Maximum lock count exceeded");
    setState(c);
    return true;
  }
  return false;
}
```

- Unsafe의 compareAndSetInt를 사용하여 락의 상태(state)를 원자적(Atomic) 으로 변경
- expect 값과 현재 state 값이 일치하면 update 값으로 변경
- CPU의 CAS(Compare-And-Swap) 명령어를 활용해 lock과 unlock을 비효율적인 synchronized 없이 처리

- lock()은 기본적으로 무한정 블로킹(blocking) 됩니다. 즉, 락을 얻을 수 있을 때까지 대기합니다.
```java
// AbstractQueuedSynchronizer
public final void acquire(int arg) {
    if (!tryAcquire(arg) && acquireQueued(addWaiter(Node.EXCLUSIVE), arg))
        selfInterrupt();
}
```

- tryAcquire(arg) → 락을 한 번 시도 (실패 시 false 반환)
- 실패하면 addWaiter(Node.EXCLUSIVE) → 대기 큐(FIFO)에서 기다리는 상태로 진입
- 이후 acquireQueued(...) 내부에서 스레드는 락을 얻을 때까지 블로킹됨

### CPU의 CAS(Compare-And-Swap) 명령어 ?
- Unsafe.compareAndSetInt()로 원자적(Atomic)으로 상태(state)를 변경하는 원리
- compareAndSetInt는 CAS(Compare-And-Swap) 연산을 이용하여 state 값을 원자적으로(Atomic) 변경하는 메서드입니다.

```java
protected final boolean compareAndSetState(int expect, int update) {
    return U.compareAndSetInt(this, STATE, expect, update);
}

// Unsafe.compareAndSetInt() 내부 동작
// offset → 메모리에서 state 필드의 위치 (Unsafe가 직접 메모리 주소 참조)
// expect → 예상되는 기존 값
// update → 변경하려는 값
public final native boolean compareAndSetInt(Object obj, long offset, int expect, int update);
```

- CAS(Compare-And-Swap)의 동작 원리
  - 현재 메모리에 있는 state 값을 읽어옴*\
  - expect 값과 현재 state 값이 같다면, state 값을 update 값으로 변경
  - 다르면 아무 동작도 하지 않고 false를 반환
  - 이 과정은 CPU의 `LOCK CMPXCHG(Compare and Exchange)` 어셈블리 명령어를 통해 실행되며, 원자적 연산(Atomic Operation)으로 동작합니다.
    - 즉, 여러 개의 스레드가 동시에 compareAndSetState(0,1)을 호출해도, 단 하나의 스레드만 성공하고 나머지는 실패하게 됩니다.
