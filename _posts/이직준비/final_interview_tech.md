## 기억에 남는 이슈
- 어드민 서버 두 대 중 1번 서버에서만 톰캣 스레드가 max까지 차고, 응답 지연이 발생
- WAS 재시작
- 톰캣 스레드 계속 점유하고 있던 요청들 확인했을때 특정 몇 개의 요청에서 점유하고 있었음
- 해당 요청들애 어떤 부분에서 지연 발생하나 살펴보니 특정 API 호출할때 readTimeout이 있음에도 계속 대기하고 있음
- 해당 api 제공하는 서버의 로그를 확인해보니, 특정 시점부터 WAS 재시작한 시간까지 1번서버로 부터의 요청이 없음
- 요청 유입이 끊기기 시작한 시각의 우리 어드민 서버 로그 확인해보니, 해당 api 호출하는 과정에서 OOM 에러 발생함
- 근데 OOM 에러 발생한 부분이 RestTemplate에서 호출하는 과정에서 inputstream을 읽기위해 2kb 버퍼를 할당하는 내부 코드에서 발생하게됨
- 힙 덤프 확인해보니 엑셀 생성시 관련된 객체들이 매우 많았고, 엑셀 조회기간이 매우 긴 요청들이 들어왔음을 확인
- 해당 RestTemplate에 세팅된 설정 확인해보니 http-con-pool 사이즈가 1, 따라서 OOM 에러로 인해 제대로 커넥션 반납이 안돼서 사용할 커넥션이 없어 readTimeout과는 상관없이
  무한 대기상태에 빠졌던 것으로 판단
- http-con 풀 사이즈 늘림, 커넥션 최대 대기 시간 세팅
- 엑셀 조회에서 불필요하게 힙에 쌓이지 않도록 로직 수정 @Transactional 제거 (1차 캐시)

**비관적 락 vs 낙관적 락**
-개인적으로 비관적 락은 동시에 여러 요청이 오는 상황에서 하나의 자원에 대한 많은 경합이 예상되고, 하나의 자원에는 하나의 요청만 접근해야 하는 경우 (데이터 일관성 매우 중요)
=> EX : 특정 계좌에 대한 잔액 갱신 / 상품권 번호 발급 요청
- 낙관적 락은 하나의 자원에 동시에 여러 요청 경합이 발생하지 않고, 발생하더라도 특정 조건을 만족하는 요청만 처리되면 되는 경우 또는 재시도, 롤백 처리에 비용이 많이 들지 않는 경우
=> EX : 최근 수량 알림 / v1,v2

## 해당 업무 관련된 전문 기술 지식 1개
- 스프링에서 `@Transactional` 어노테이션을 사용했을 때 어떻게 메서드가 끝날 때까지 하나의 DB 커넥션이 계속 사용될 수 있는 것인지 궁금하여 내부 동작 방식을 살펴본 경험이 있습니다.
  - 이를 통해, 하나의 트랜잭션에서 사용되는 DB 커넥션을 관리하기 위해 `ConnectionHolder`라는 별도의 객체가 존재하고 이를 `Thread`, `DataSoruce` 단위로 관리하기 위해 내부적으로 `TheradLocal`을 사용한다는 것을 알게 되었습니다.
  - 따라서, 비동기로 처리되는 부분은 왜 트랜잭션 보장이 안되는지에 대해서도 자연스럽게 이해할 수 있었습니다.
  - 또한 `REQUIRES_NEW`와 같은 트랜잭션 전파 레벨이 필요한 메서드를 호출할 때 기존 트랜잭션에 대한 `ConnectionHolder`는 `SuspendedResourcesHolder` 객체에서 관리되고 있어서, 새로운 트랜잭션이 종료된 후에도 기존 커넥션을 사용할 수 있음을 알게 되었습니다.
