## 1. 정의

---

> CORS는 출처(origin)가 다른 서버의 응답을 현재 페이지의 JS에 넘겨도 되는지 판단하는 브라우저 표준([Fetch 표준](https://fetch.spec.whatwg.org/#http-cors-protocol))이다. <br>

* **Cross-Origin** : 출처가 다른
* **Resource** : URL로 요청하는 모든 자원 (응답 본문이 없는 경우도 포함)
* **Sharing** : 공유할지

현재 페이지와 요청 URL의 `{scheme}://{host}:{port}`가 모두 같을 때 '동일한 출처'로 본다.

## 2. 목적

---

> [SOP(Same-Origin Policy)](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) 때문에 브라우저가 출처가 다른 서버의 응답을 읽을 수 없던 **제약을 서버가 허락한 경우에 한해 안전하게 풀어 주기 위함**이다.

* 브라우저는 SOP 제약 때문에 출처가 다른 [서버의 응답을 읽을 수](/posts/cors-response-reading-flow/) 없었다.
* 웹 서비스가 발전하면서 이 제약을 풀어야 하는 상황이 생겼다.
* 그래서 SOP 제약을 **안전하게 허용하는 방법**으로 CORS가 등장했다.

## 3. 배경

---

### SOP 제약이 도입된 이유와, 없을 때의 악용 예시

* JS가 도입되면서 페이지 안에서 응답을 프로그래밍적으로 다룰 수 있게 됐고, 그만큼 악용 범위도 넓어졌다.
* 브라우저는 요청에 사용자의 쿠키를 자동으로 붙이고, 사용자 기기의 네트워크 위치에서 요청을 보낸다.
* SOP가 없으면 아무 사이트의 JS나 사용자 브라우저를 빌려
  * 사용자 자격으로 로그인된 응답(개인 데이터)을 읽거나
  * 공격자는 직접 닿을 수 없고 사용자 기기에서만 닿는 곳(사내망, 공유기·IoT, localhost 등)의 응답을 읽어 외부로 보낼 수 있다.

### CORS : 나중엔 왜 제약을 벗어나야 했을까?

* 막아야 하는 정보도 있지만, 모두에게 공개하고 싶은 정보도 있다. (예: 기상 데이터)
* 허용한 특정 출처에서만 쓰게 하고 싶은 경우도 있다. (예: 계약한 파트너에게만 시세 제공)
* 표준이 없어서 JSONP 같은 위험한 우회책이 쓰였고, CORS는 이를 안전한 정식 경로로 대체했다.

<details markdown="1">
<summary><span>참고 : JSONP 우회 방식</span></summary>

> `<script src>`는 다른 origin이어도 불러와서 **실행**할 수 있다는 점(임베딩 허용)을 이용한 우회다.

**① 받을 함수를 미리 정의한다 (a.com)**

```html
<script>
  function handleWeather(data) {
    console.log(data.temp); // 12 → 다른 origin 데이터를 JS가 손에 쥠
  }
</script>
```

**② `<script>` 태그로 요청하면서 함수 이름을 넘긴다**

```html
<script src="https://api.weather.com/today?callback=handleWeather"></script>
```

**③ 서버는 JSON을 함수 호출로 감싼 JS 코드로 응답한다**

```js
handleWeather({ "city": "Seoul", "temp": 12 });
```

**④ 브라우저가 이를 스크립트로 실행한다** → a.com의 `handleWeather`가 호출되며 데이터가 전달된다.

응답을 "읽은" 게 아니라 "실행"한 것이라 SOP에 걸리지 않는다.

**위험한 이유**

| 문제 | 설명 |
| --- | --- |
| 제공자를 완전히 믿어야 함 | 응답이 데이터가 아니라 **실행되는 코드**다. 서버가 해킹되면 임의 코드가 a.com 페이지에서 실행된다 |
| 허락 대상을 고를 수 없음 | `<script>` GET 요청엔 `Origin` 헤더가 없어 누가 불렀는지 알기 어렵다 → 아무 사이트나 호출 가능 |
| 사용자별 데이터면 그대로 유출 | `<script>` 요청에도 쿠키가 붙는다. `bank.com/me?callback=x`가 JSONP를 지원하면 evil.com이 태그 하나로 로그인 사용자 정보를 가져간다 (SOP가 막으려던 공격) |
| 기능 제약 | GET만 가능, 헤더 지정 불가, 상태 코드 기반 에러 처리가 어려움 |

**CORS와 비교**

| | JSONP | CORS |
| --- | --- | --- |
| 원리 | 스크립트 임베딩 허용을 이용한 우회 | 서버가 헤더로 읽기를 정식 허락 |
| 응답 형태 | 실행되는 JS 코드 | 데이터 (JSON 그대로) |
| 허락 대상 지정 | 사실상 불가 | `ACAO`로 origin 지정 |
| 쿠키 포함 응답 | 무조건 노출 | `ACAC` + origin 명시해야만 허용 |
| 메서드 | GET만 | 모든 메서드 (preflight) |

</details>

### 왜 서버의 허락이 필요했을까?

* 이 자원을 어디서 써도 되는지는 자원을 가진 서버만 안다. 그래서 서버가 결정하고 브라우저가 집행한다.
* 기본값이 거부인 opt-in 방식이다.
  * CORS를 모르는 서버는 '허락해야 한다'는 사실조차 모른다. 관련 헤더가 없으면 허락하지 않은 것으로 본다.
  * 덕분에 기존 서버는 아무것도 바꾸지 않아도 안전하다.
  * 쿠키가 실린 응답은 한 번 더 허락이 필요하다. (`ACAC: true` + origin 명시)

## 4. 동작 방식

---

> 서버는 응답 헤더로 허락하고, 브라우저는 그 헤더를 보고 응답을 JS에 넘길지 판별한다.

### 기본 흐름

> 단순 요청인지 preflight 대상 요청인지에 따라 흐름이 갈린다.

**단순 요청**

```text
[a.com 페이지 JS] fetch('https://api.b.com/orders', { credentials: 'include' })
   ▼
[브라우저] 요청에 Origin: https://a.com 헤더를 붙여 전송
   ▼
[서버 b.com] 허용 목록에 a.com이 있으면 응답 헤더에 허락을 붙임
             Access-Control-Allow-Origin: https://a.com
             Access-Control-Allow-Credentials: true   ← 쿠키 등 자격 증명이 실린 요청까지 허락할 때
   ▼
[브라우저] 응답 헤더 확인
   ├─ ACAO가 내 origin(또는 *)이고, credentials 모드가 include면 ACAC도 true → JS에 응답 전달
   └─ 아니면 → 응답 폐기, JS에는 TypeError
```

**Preflight 대상 요청** (PUT · DELETE, JSON 본문, 커스텀 헤더 등 `<form>`으로는 못 보내던 요청)

```text
[브라우저] 본 요청 전에 사전 요청을 먼저 보냄 (쿠키 없이)
           OPTIONS /orders
           Origin: https://a.com
           Access-Control-Request-Method: PUT
           Access-Control-Request-Headers: content-type
   ▼
[서버] 허락하면
           Access-Control-Allow-Origin: https://a.com
           Access-Control-Allow-Methods: PUT
           Access-Control-Allow-Headers: content-type
           Access-Control-Allow-Credentials: true
   ▼
[브라우저] 허락 확인
   ├─ 통과 → 본 요청 전송 → 이후는 단순 요청과 같은 흐름
   └─ 실패 → 본 요청을 아예 보내지 않음
```

* 이 사전 요청을 **preflight 요청**이라 한다. (표준 명칭 : **CORS-preflight request**)
  * `OPTIONS` 메서드로 `Access-Control-Request-Method` · `Access-Control-Request-Headers`를 실어 보내며, **쿠키 없이** 보낸다.
* 단순 요청은 서버가 이미 처리한 뒤 **읽기만** 막고, preflight 대상은 **본 요청 자체를** 막는다.

<details markdown="1">
<summary><span>Preflight 요청이 필요한 이유</span></summary>

* CORS 이전에는 다른 origin으로 보낼 수 있는 요청이 `<form>`이 보낼 수 있는 범위로 한정되어 있었다.
  * 예) JSON 본문의 POST, PUT · DELETE, 커스텀 헤더가 붙은 요청은 다른 origin에서 올 수 없었다.
* 그래서 서버도 이런 요청이 다른 출처에서 오리라 생각하지 않고 별다른 검증을 하지 않을 수 있다.
* CORS가 등장하면서 JS(`fetch`, XHR. axios · jQuery `$.ajax` 같은 라이브러리도 내부적으로 이 둘을 쓴다)로 이런 요청도 다른 origin에 보낼 수 있게 됐다.
  * 그런데 이런 요청을 바로 보내면, 위처럼 다른 출처의 요청을 가정하지 않은 서버에서는 악의적인 요청이 그대로 처리될 수 있다.
  * 그래서 브라우저는 본 요청 전에 사전 요청을 보내고, 응답의 ACAO · ACAC · `Access-Control-Allow-Methods` · `Access-Control-Allow-Headers`를 검증해 본 요청을 보내도 되는지 확인한다.
  * CORS 처리가 되어 있지 않은 서버는 ACAO를 응답하지 않으므로, 브라우저가 본 요청을 내보내지 않는다.
  * 즉 단순 요청은 보내는 것 자체는 서버 허락과 무관하고 응답 읽기만 허락에 달려 있지만, preflight 대상 요청은 **보내는 것 자체가 서버의 허락에 달려 있다.**
* 반대로 `<form>`으로도 보낼 수 있던 범위의 요청(단순 요청)은 새로운 위험이 아니므로 preflight 없이 바로 보낸다.

</details>

<details markdown="1">
<summary><span>Preflight 요청이 발생하는 상황</span></summary>

> **요청 대상 · 모드가 오른쪽**이고, 나머지 세 조건(메서드 · 헤더 · `Content-Type`) 중 **하나라도 오른쪽**이면 preflight(`OPTIONS`)를 먼저 보낸다. 그 외에는 preflight 없이 바로 전송한다.
>
> 요청 대상 · 모드는 아래 "모든 요청이 검사 대상은 아니다" 참고

| 구분 | preflight 없음 | preflight 대상 |
| --- | --- | --- |
| 요청 대상 · 모드 | same-origin 요청, 또는 `navigate` · `no-cors` 모드 | **cross-origin + `cors` 모드** (`fetch`, XHR 등) |
| 메서드 | `GET`, `HEAD`, `POST` | `PUT`, `DELETE`, `PATCH` 등 |
| 헤더 | **CORS-safelisted 헤더만** (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`(아래 3종), `Range`) | `Authorization`, `X-Requested-With` 같은 커스텀 헤더 추가 |
| `Content-Type` | `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` (또는 body 없음) | `application/json` 등 그 외 |

same-origin이면 JSON `PUT`이어도 preflight가 없고, `navigate` · `no-cors`는 애초에 단순한 메서드 · 헤더만 보낼 수 있다.
* 메서드 · 헤더 · `Content-Type`이 모두 왼쪽인 요청을 **단순 요청**이라 부른다.

</details>

<details markdown="1">
<summary><span>참고 : Preflight 검증이 통과하는 조건</span></summary>

> 아래를 모두 만족해야 통과한다.

```text
1. 상태 코드가 2xx
2. Access-Control-Allow-Origin이 내 Origin(또는 *)
3. credentials 모드가 include면 Access-Control-Allow-Credentials: true
4. 단순 메서드가 아니거나 커스텀 헤더를 쓰면 Allow-Methods, Allow-Headers에 그 값이 포함
```

</details>

### 모든 요청이 검사 대상은 아니다

> CORS의 목적은 허락받지 않은 출처의 JS가 응답을 읽어 악용하는 것을 막는 것이다. <br>
> 따라서 cross-origin 응답이라도 그 응답이 **페이지의 JS에 넘어가지 않는 요청이면 검사할 필요가 없다.** <br>
> **cross-origin**이면서 **`cors` 모드**인 요청만 검사한다.

검사 대상이 아닌 요청의 응답에도 서버가 ACAO · ACAC를 붙일 수 있다. (nginx 일괄 설정, `Origin`이 실린 `<form>` POST 등) 브라우저가 보지 않으므로 효과는 없다.

<details markdown="1">
<summary><span>cross-origin 요청</span></summary>

**출처 관계**

> 요청을 시작한 문서와 요청 URL의 관계는 브라우저가 요청 헤더 `Sec-Fetch-Site`로 알려 준다. 값은 아래 넷 중 **가장 좁은 하나**로 정해진다.

cross-origin은 표의 **same-site 또는 cross-site**인 경우다.

| 관계 | 기준 | 예시 (`https://app.example.com` 기준) | `Sec-Fetch-Site` | CORS (origin 기준) |
| --- | --- | --- | --- | --- |
| same-origin | scheme · host · port 모두 같음 | `https://app.example.com/api/orders` | `same-origin` | 검사 없음 |
| same-site (origin은 다름) | origin은 다르지만 scheme · eTLD+1이 같음 | `https://foo.example.com`, `https://app.example.com:8443` | `same-site` | **검사 대상** |
| cross-site | eTLD+1 또는 scheme이 다름 | `https://evil.com`, `http://app.example.com` | `cross-site` | **검사 대상** |
| none | 시작한 문서가 없음 | 주소창 입력, 북마크 | `none` | 해당 없음 |

* 포함 관계로 보면 **same-origin ⊂ same-site**다.
  * scheme · host가 같으면 eTLD+1도 같으니 same-origin 요청은 당연히 same-site다.
  * 다만 `Sec-Fetch-Site`는 더 좁은 `same-origin`으로 표시하므로, 표의 same-site 행은 "same-site이면서 origin은 다른" 경우만 뜻한다.
* CORS는 origin을, SameSite는 site를 기준으로 하므로 **같은 요청이 "CORS로는 cross-origin, SameSite로는 same-site"일 수 있다.** 형제 서브도메인이 이 경우다.
* scheme이 다르면 eTLD+1이 같아도 cross-site다. (schemeful same-site)

</details>

<details markdown="1">
<summary><span>요청 모드</span></summary>

> 모드는 요청이 cross-origin일 때(리다이렉트로 cross-origin이 되는 경우 포함) **CORS를 적용할지, 응답을 어디까지 보여 줄지**를 정한다. 실제 모드는 요청 헤더 `Sec-Fetch-Mode`에 담긴다.
>
> 모드는 **요청 방법**으로 정해지고, 목적지가 same-origin인지와는 무관하다. 목적지와의 관계는 `Sec-Fetch-Site`가 따로 알려 준다.
>
> * `Sec-Fetch-Mode: cors` = "cross-origin이면 CORS를 적용하겠다"는 요청 방식 (`fetch()` 기본값)
> * `Sec-Fetch-Site: same-origin` = 실제로는 같은 origin으로 보냄 → CORS 검사가 일어나지 않음
> * 그래서 둘이 `same-origin` + `cors`로 함께 찍히는 건 정상이다. 리다이렉트로 목적지가 바뀔 수 있어서 모드는 요청 시작 시점에 미리 정해진다.

| 모드 | 의미 | 쓰는 곳 | `Origin` 헤더 | cross-origin 응답 처리 |
| --- | --- | --- | --- | --- |
| `navigate` | 문서(페이지 · iframe)를 불러오는 이동 | 주소창, 링크, `<form>` 제출, iframe | POST면 붙음, GET은 안 붙음 | CORS 검사 없음. 응답은 문서로 열리고 다른 origin의 JS는 못 읽음 |
| `no-cors` | 내용을 안 보는 조건으로 다른 origin 리소스 사용 | `<img>`, 일반 `<script>`, `<link rel=stylesheet>`, `fetch(url, {mode: 'no-cors'})` | POST면 붙음, GET은 안 붙음 | CORS 검사 없음.<br>응답은 **불투명**(JS가 상태 · 헤더 · 본문 못 봄). 단순 메서드 · 헤더만 허용 |
| `cors` | 내용까지 정식으로 받겠다는 요청 | `fetch()` 기본값, XHR, 모듈 스크립트, `crossorigin` 속성, 웹폰트 | 붙음 | **CORS 검사 대상**. ACAO 없으면 실패. 단순 요청이 아니면 preflight |
| `same-origin` | 같은 origin만 허용 | `fetch(url, {mode: 'same-origin'})`, 클래식 Worker 스크립트 | (same-origin 규칙과 같음) | cross-origin이면 요청을 보내지 않고 바로 에러 |
| `websocket` | WebSocket 연결 | `new WebSocket(...)` | 항상 붙음 | **CORS 검사 없음**. 서버가 `Origin`을 직접 검사하지 않으면 다른 사이트가 쿠키를 실어 연결 가능 (CSWSH) |

**불투명(opaque) 응답**

> `Response.type === 'opaque'`인 응답이다. status는 `0`, 헤더는 비어 있고, body는 `null`이다. <br>
> 브라우저는 이 응답을 **쓰기만 하고 JS에 내용을 보여 주지 않는다.** 예를 들어 `<img>` 렌더링이나 Service Worker 캐시 저장에는 쓰이지만, JS는 요청이 성공했는지조차 알 수 없다.

| 요청 방법 | 모드 | cross-origin일 때 동작 |
| --- | --- | --- |
| 주소창, 링크, `<form>` 제출 (iframe 포함) | `navigate` | 그냥 이동. 응답은 새 페이지가 됨 |
| `<img>`, `<link rel=stylesheet>`, 일반 `<script>` (`crossorigin` 없음) | `no-cors` | 로드는 됨. 대신 JS가 내용을 못 들여다봄 (불투명 응답) |
| `crossorigin` 속성이 붙은 `<img>` · `<script>` · `<link>` | `cors` | ACAO가 없으면 로드 실패 |
| `<script type="module">` | `cors` (항상) | 위와 같음 |
| `@font-face` 웹폰트 | `cors` (항상) | 위와 같음 |
| `fetch()` (기본값), XHR | `cors` | 위와 같음. 응답 읽기도 ACAO로 판단 |

</details>

## 5. Access-Control-Allow-Origin, Access-Control-Allow-Credentials

---

> 서버가 허락을 담아 보내는 응답 헤더는 `Access-Control-Allow-Origin`(ACAO), `Access-Control-Allow-Credentials`(ACAC) 두 개이고, 브라우저는 이 두 값을 보고 응답을 JS에 넘길지 판별한다.

### Access-Control-Allow-Origin (ACAO)

* 서버가 "이 origin의 JS에는 응답을 보여 줘도 된다"고 허락한 origin이다.
* 목록이 아니라 **값 하나**다. 정확한 origin 하나, `*`, `null` 중 하나가 들어간다.
  * 값이 여러 개이거나 헤더가 2개면 브라우저가 거부한다.
* 서버는 허용 목록을 들고 있다가 **요청 `Origin`과 일치하는 것 하나를 그대로 돌려준다**(echo). Spring도 이렇게 동작한다.
* 브라우저는 이 값이 현재 페이지의 origin과 같으면(또는 `*`면) 응답을 JS에 전달한다.

### Access-Control-Allow-Credentials (ACAC)

* [Fetch 표준의 자격 증명(credentials)](https://fetch.spec.whatwg.org/#credentials)은 **쿠키, TLS 클라이언트 인증서, 브라우저가 관리하는 HTTP 인증(Basic 등)** 세 가지다.
  * JS가 직접 넣는 `Authorization` 헤더는 여기에 해당하지 않는다. 커스텀 헤더라서 preflight 대상이 될 뿐이다.
* 요청이 자격 증명을 실을 수 있는지는 요청의 [credentials 모드](https://fetch.spec.whatwg.org/#concept-request-credentials-mode)가 정한다.

| credentials 모드 | 자격 증명 첨부 | 지정 방법 |
| --- | --- | --- |
| `omit` | 항상 안 실음 | `fetch(url, {credentials: 'omit'})` |
| `same-origin` | same-origin 요청에만 실음 | `fetch()` 기본값, XHR 기본값 |
| `include` | cross-origin 요청에도 실음 | `fetch(url, {credentials: 'include'})`, `xhr.withCredentials = true` |

* cross-origin 요청의 모드가 `include`이면 ACAO가 허용된 출처여도 ACAC가 `true`여야 응답을 JS에 전달한다.
* 기준은 **자격 증명이 실제로 실렸는지가 아니라 모드**다.
  * 모드가 `include`이면 아래 제약이 적용된다. ([Fetch 표준의 CORS check](https://fetch.spec.whatwg.org/#concept-cors-check)는 `credentials mode`만 본다)

<details markdown="1">
<summary><span>credentials 모드가 include일 때의 제약</span></summary>

* ACAO에 `*`를 쓸 수 없고 정확한 origin이어야 한다.
  * `*` + 쿠키를 허용하면 아무 사이트의 JS나 로그인된 응답(개인 정보)을 읽게 되어 SOP가 없는 것과 같아진다.
  * 그래서 쿠키가 실린 응답은 서버가 믿는 출처를 명시해 의식적으로 허락하도록 강제한다.
  * 단, 서버가 요청 `Origin`을 검사 없이 그대로 돌려주면 결과는 `*`와 같으므로, 허용 목록과 일치할 때만 돌려줘야 한다.
* ACAC가 `true`여야 한다.
* `Access-Control-Allow-Methods` · `Access-Control-Allow-Headers`에도 `*`를 쓸 수 없다.

</details>

### 두 헤더의 관계 : ACAO가 '인증', ACAC가 '인가'인 것은 아니다

> 둘 다 **origin에 대한 허락**이고 사용자와는 무관하다.
>
> * ACAO : "이 origin에 응답을 보여 줘도 된다"
> * ACAC : "자격 증명이 실린 응답도 보여 줘도 된다"
>
> 열쇠 두 개가 모두 있어야 열리는 구조다.

### ACAO, ACAC는 언제 누가 붙여 주나

> Nginx, Spring Boot 운영 환경을 가정한다.

Nginx에서도 붙일 수 있지만, 일반적으로는 Spring MVC에 CORS 설정을 둔다.

```text
요청 → Tomcat → 서블릿 필터들(SSO, SecurityHeader …)
     → DispatcherServlet
        → HandlerMapping: 핸들러를 찾고, CORS 설정이 있으면 CorsInterceptor를 끼움
        → CorsInterceptor.preHandle → DefaultCorsProcessor   ← 여기서 헤더 붙임 (org.springframework.web.cors.DefaultCorsProcessor#handleInternal)
        → 컨트롤러 실행
     → 응답
```

* 검사는 요청 헤더에 `Origin`이 있고 **서버가 보는 자기 origin과 다를 때**만 한다. (6장 검사 흐름 3단계)
* `AbstractHandlerMapping.getHandler()`가 `CorsInterceptor`(preflight면 `PreFlightHandler`)를 끼우고, 실제 검사와 헤더 추가는 `DefaultCorsProcessor`가 한다.

<details markdown="1">
<summary><span>참고 : 예시 코드</span></summary>

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")                       // 이 경로에만 CorsInterceptor 적용
                .allowedOrigins("https://app.example.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowCredentials(true)
                .maxAge(3600);
        registry.addMapping("/public/**")                    // 경로별로 다르게 설정 가능
                .allowedOrigins("*");                        // credentials 없이 전체 공개
    }
}
```

```java
@RestController
@RequestMapping("/api/orders")
@CrossOrigin(origins = "https://app.example.com", allowCredentials = "true")   // 클래스 전체
public class OrderController {

    @GetMapping
    public List<Order> list() { ... }                        // 클래스 설정 적용

    @CrossOrigin(origins = "https://partner.example.com")    // 메서드 설정이 클래스 설정과 합쳐짐
    @GetMapping("/export")
    public byte[] export() { ... }
}
```

</details>

## 6. 서버도 Origin을 검사한다 : Spring Web MVC 기준

---

> CORS 표준은 브라우저만 검사하지만, Spring은 서버에서도 `Origin`을 검사해서 허용되지 않은 Origin이면 **컨트롤러를 실행하지 않고 403**으로 거부한다. <br>
> 브라우저 검사를 대체하는 것은 아니고, 아래 단계를 순서대로 통과한 요청에만 적용된다.

<details markdown="1">
<summary><span>검사 흐름</span></summary>

| 단계 | 조건 | 해당하지 않으면 |
| --- | --- | --- |
| 1. DispatcherServlet 도달 | 앞단 서블릿 필터가 응답을 끝내지 않음 | CORS 처리 없음 (헤더도 안 붙음) |
| 2. 설정 매칭 | 요청 경로에 맞는 설정이 있음 (`addMapping` 경로, `@CrossOrigin`) | 본 요청은 그대로 통과, preflight는 403 |
| 3. CORS 요청인가 | `Origin`이 있고, 서버가 보는 자기 scheme · host · port와 다름 (`CorsUtils.isCorsRequest`) | 검사 없이 통과 (`Vary`만 붙음) |
| 4. ACAO 미설정 | 앞단(`CorsFilter`, Security `http.cors()`, 직접 만든 필터 등)이 이미 ACAO를 붙이지 않음 | 중복 방지를 위해 건너뜀 |
| 5-a. preflight | Origin · 메서드 · 헤더 검사 | 허용이면 컨트롤러 없이 200 + `Access-Control-Allow-*`, 아니면 403 |
| 5-b. 본 요청 | Origin · 메서드 검사 | 허용이면 ACAO/ACAC를 붙이고 컨트롤러 실행, 아니면 **403 `Invalid CORS request`** (컨트롤러 실행 안 됨) |

* 5-b의 403은 **CORS 표준이 요구하는 동작이 아니라 Spring의 구현**이다.
  * 허용 안 된 Origin의 단순 요청도 서버 단에서 막히는 효과가 있지만, 1~3단계에서 빠지는 요청은 이 검사를 거치지 않는다.
* 4단계의 "앞단"은 같은 WAS 안에서 먼저 실행되는 필터 · 인터셉터다.
  * nginx 같은 외부 프록시가 붙이는 헤더는 Spring이 볼 수 없어서, 둘 다 붙이면 ACAO가 2개가 되어 브라우저가 거부한다.

</details>

* 브라우저의 CORS는 응답 읽기만 막는다. 요청은 이미 서버에 도착해 처리되고, 상태 변경도 일어날 수 있다.
* 반면 서버가 403으로 거부하면 요청 처리 자체가 막힌다. 결과적으로 **Origin 검사 방식의 CSRF 방어 효과**가 생긴다.

### Origin이 요청 헤더에 포함되는 상황

| 출처 관계 | 요청 | 모드 | `Origin` 헤더 | 서버(Spring) 검사 |
| --- | --- | --- | --- | --- |
| same-origin | 페이지 이동, 일반 `<script>` · `<img>` (GET · HEAD) | `navigate` · `no-cors` | 없음 | ✕ |
| same-origin | 모듈 스크립트, `crossorigin` 속성, 웹폰트 (GET) | `cors` | 있음 | △ ※ |
| same-origin | POST · PUT · DELETE 등 | 무관 | 있음 | △ ※ |
| cross-origin | `fetch` · XHR · 모듈 스크립트 등 (메서드 무관) | `cors` | 있음 | ○ |
| cross-origin | `<form>` POST 제출 | `navigate` | 있음 | ○ |
| cross-origin | 링크 이동, `<img>` · 일반 `<script>` (GET) | `navigate` · `no-cors` | 없음 | ✕ |
| 브라우저 밖 | curl, 서버 간 호출 | - | 보통 없음. 임의 값도 가능 | `Origin`을 넣었을 때만 |

※ 서버가 보는 자기 origin(scheme · host · port)이 브라우저 주소와 같으면 ✕, 프록시 뒤라서 다르게 보이면 cross-origin으로 판별해 검사한다.
