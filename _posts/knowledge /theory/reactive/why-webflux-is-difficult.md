
> spring webflux의 어떤 부분이 러닝 커브를 높이는거야 ?

## 1. 리액티브 프로그래밍 패러다임 이해
- Spring WebFlux는 리액티브 프로그래밍 모델을 기반으로 하고 있으며, 이는 전통적인 명령형 프로그래밍과 매우 다릅니다.
- 개발자는 다음과 같은 새로운 개념을 이해해야 합니다:
  - Publisher/Subscriber 모델 (Reactive Streams 표준)
  - Mono와 Flux 같은 리액티브 타입
  - 비동기 처리 흐름과 데이터 스트림 관리
  - 백프레셔(Back Pressure) 개념
  - 이러한 개념들은 처음 접하는 개발자들에게 직관적이지 않을 수 있어 학습 곡선을 높입니다.

## 2. 논블로킹 I/O 모델의 복잡성
- WebFlux는 논블로킹 I/O를 사용하므로 개발자는:
  - 논블로킹 코드를 작성하는 방법을 배워야 합니다.
  - 전통적인 블로킹 방식과의 차이점을 이해하고 전환해야 합니다.
  - 공유 자원을 처리하는 방법(예: DB 연결, 파일 처리)을 새롭게 설계해야 합니다.

## 3. 디버깅과 문제 해결의 어려움
- 리액티브 코드는 일반적으로:
  - 비동기로 실행되기 때문에 디버깅이 어렵습니다.
  - 호출 스택이 명확하지 않아서 오류 추적이 더 복잡합니다.
  - 코드의 실행 순서를 이해하기 어려울 수 있습니다.

## 4. 리액티브 API 사용
- WebFlux를 효과적으로 사용하려면 리액티브 스타일을 지원하는 리액티브 데이터베이스 드라이버(예: R2DBC)나 리액티브 HTTP 클라이언트를 사용해야 합니다.
- 기존 블로킹 API는 WebFlux와 호환되지 않기 때문에:
  - 기존 코드를 리팩토링하거나
  - 새로운 리액티브 API를 학습해야 합니다.

## 5. 생태계와 도구 부족
- Spring WebFlux는 Spring MVC보다 비교적 새로운 기술이므로:
  - 자료나 예제가 제한적일 수 있습니다.
  - 전통적인 MVC 스타일의 라이브러리와 통합이 까다롭습니다.
  - 테스트 작성과 모니터링 도구의 설정이 기존 환경보다 복잡할 수 있습니다.

## 6. 전통적인 사고 방식의 전환 필요
- 리액티브 프로그래밍은 개발자가:
  - "요청-응답" 흐름을 넘어 스트림 기반으로 사고해야 합니다.
  - 동시성과 상태 관리를 완전히 새롭게 이해해야 합니다.
  - 코드가 아닌 데이터 흐름 중심으로 설계를 전환해야 합니다.
