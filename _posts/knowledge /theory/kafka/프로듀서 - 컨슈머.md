
## 이벤트가 컨슈머까지 전달되고 처리되는 흐름 (간략하게)
---

### 1. 이벤트 전달 (프로듀서 - 브로커)
프로듀서 (이벤트 발행) --> 브로커
~~브로커에서 in.sync.replicas 설정된 수만큼 파티션에 복제 완료했으면 프로듀서로 ack(?)~~
→ 정정: ack 시점은 프로듀서의 acks 설정이 결정 (0: 안 기다림 / 1: 리더 파티션에 쓰이면 / all: ISR 전부에 복제되면)
→ min.insync.replicas는 "이만큼 복제되면 ack"가 아니라 acks=all일 때 요구되는 ISR 최소 하한. 미달이면 브로커가 쓰기 자체를 거부
보완: 복제는 리더 파티션 → 다른 브로커의 팔로워 레플리카로 일어남. send()도 즉시 전송이 아니라 배치(record accumulator)에 쌓였다가 전송됨

### 2. 이벤트 수신 (브로커 - 컨슈머)
~~컨슈머에 세팅된 주기로 브로커에서 polling~~
→ 정정: 폴링 "주기" 설정은 없음. 애플리케이션 루프가 poll()을 직접 호출하는 구조 (max.poll.interval.ms는 주기가 아니라 poll 간격의 상한, 넘기면 그룹에서 퇴출)
→ poll 하는 시점: while(true) { records = poll(); 레코드 처리; (커밋) } 루프라서, 직전 poll로 받아온 레코드들의 처리가 끝나면 곧바로 다음 poll.
즉 poll 간격 = 배치 처리 시간이고, 처리가 빠르면 poll도 잦아짐 (Spring Kafka 등 프레임워크도 내부적으로 이 루프를 돌려줌)

→ 받아올 레코드가 없으면 poll()은 브로커에서 fetch.max.wait.ms만큼 대기했다가 빈손으로 리턴 → 다시 poll (busy-loop 방지용 long polling)
~~브로커는 해당 컨슈머 그룹이 해당 파티션의 어떤 오프셋부터 레코드 전달해야하는지 판단하여 전송~~
→ 정정: 컨슈머가 자기 position(다음 읽을 오프셋)을 메모리에 들고 있고, fetch 요청에 "이 오프셋부터"라고 명시해서 요청. 브로커가 판단하지 않음
→ 커밋된 오프셋은 컨슈머 (재)시작·리밸런싱으로 파티션을 새로 할당받을 때 시작 위치 복원용으로만 쓰임 (기록 없으면 auto.offset.reset)
보완: 컨슈머 그룹 내에서 한 파티션은 한 컨슈머만 소비. 파티션 할당은 그룹 코디네이터(브로커)가 주관
보완: 컨슈머는 high watermark(HW = ISR 전원에 복제 완료된 지점)까지만 읽을 수 있음. 리더에만 쓰이고 복제 중인 레코드는 fetch 요청이 와도 안 줌 (복제 전 레코드를 읽었는데 리더가 죽으면 "존재한 적 없는 데이터"를 읽은 셈이 되므로).
이건 프로듀서 acks 설정과 무관 — acks=1로 ack 받았어도 컨슈머는 ISR 복제 완료 후에야 보임

### 3. 이벤트 처리
~~컨슈머에서 처리완료하면 브로커 측으로 오프셋 커밋~~
→ 정정: 기본값은 auto commit(enable.auto.commit=true). "처리 완료 후 커밋"은 auto commit 끄고 commitSync/commitAsync를 직접 호출하는 경우
→ auto commit 동작: 백그라운드 타이머가 아니라 poll() 안에서 일어남. poll() 호출 시마다 "마지막 auto commit 후 auto.commit.interval.ms(기본 5초) 지났나?" 체크
→ 지났으면 직전 poll이 리턴했던 레코드들의 오프셋(현재 position)을 커밋.
즉 실제 커밋 간격은 정확히 5초가 아니라 "5초 이상, poll 주기에 따라"이고, poll을 안 부르면 커밋도 안 됨 (close()·리밸런싱 시에도 커밋함)
→ 커밋되는 값은 "처리한 마지막 오프셋"이 아니라 "다음에 읽을 오프셋"(마지막 처리 + 1)
→ auto commit 유실 케이스: 커밋 대상이 "처리 완료한 오프셋"이 아니라 "poll로 받아간 오프셋"이라서 생김
- 동기 루프(poll → 배치 전부 처리 → 다음 poll)면 커밋 시점엔 처리가 끝나 있으니 유실 없음 (중복만 가능)
- 받은 배치를 별도 스레드에 넘기고 바로 다음 poll 도는 비동기 처리면, 아직 처리 중인 레코드 오프셋이 커밋됨 → 크래시 후 재시작하면 커밋 지점부터 읽어서 미처리 레코드 건너뜀 → 유실
- 배치 처리 중 예외를 삼키고 루프 계속 도는 경우도 동일 (실패 레코드까지 커밋됨)

### 4. 오프셋 기록
~~브로커는 오프셋 기록하고 모든 파티션에 전파 ??~~
→ 정정: 커밋된 오프셋은 __consumer_offsets 내부 토픽에 (그룹, 토픽, 파티션) 키로 저장됨. 커밋 요청은 그룹 코디네이터 브로커가 처리. "전파" 같은 동작은 없음 (토픽 자체가 복제될 뿐)
~~프로듀서 쪽에도 알리는게 있나 ??~~
→ 정정: 없음. 프로듀서와 컨슈머는 완전히 분리돼 있고, 프로듀서는 컨슈머 오프셋의 존재를 모름


## 동일한 이벤트 중복 발행 / 수신이 발생하는 시나리오
---

### 1. 프로듀서 - 브로커 구간
~~프로듀서에서 발행한 이벤트가 네트워크 이슈 등으로 유실되어 브로커에 전달 안됨 (네트워크 이슈 말고 또 다른 경우?)~~
~~ack를 받지 못했기 때문에, 브로커로 재발행 (at-least-once인 경우 ? => 즉, 프로듀서에서 재처리 시나리오 있는 경우 ?)~~
→ 정정: 요청 자체가 유실된 경우의 재발행은 중복이 아니라 정상 재시도 (브로커에 안 쓰였으니 결과는 1건). 중복이 생기는 건 2번처럼 "브로커에는 쓰였는데 ack가 유실/지연된 경우"뿐
→ 네트워크 외의 재시도 유발 원인: 리더 선출 중 에러, request.timeout.ms 초과 (브로커는 결국 썼는데 응답이 늦은 경우 → 이건 중복 유발)
→ at-least-once는 별도 옵트인이 아니라 프로듀서 기본 설정(acks=all + 재시도)이 이미 at-least-once

### 2.프로듀서 - 브로커 구간
위와 비슷하게 브로커에서 ack 보낸게 프로듀서에 전달이 안됨
프로듀서에서는 이벤트 재발행 → 여기서 중복 발생
~~idempotence producer(맞나?) 사용하면, 브로커에서 해당 프로듀서 id와 이벤트 seq 기록해놓고 있기 때문에, 오프셋 변경하지 않음 ??~~
→ 정정: idempotent producer(enable.idempotence=true, Kafka 3.0부터 기본 활성화). 브로커가 PID + 파티션별 시퀀스 번호를 기록해두고, 중복 시퀀스가 오면 로그에 다시 append하지 않고 버린 뒤 ack만 응답
→ 한계: 같은 프로듀서 세션 + 같은 파티션 내 중복만 막음. 앱 재시작 후 같은 메시지를 다시 send()하는 건 못 막음

### 3. 브로커 - 컨슈머 구간
컨슈머가 이벤트 처리 후 오프셋 커밋한게 유실되어 브로커에 전달 안됨
다음 polling 때 동일한 이벤트 재수신
이벤트 처리 후 오프셋 커밋하려는데, 롤링배포로 인해 컨슈머 다운돼서 커밋이 안됨 (리밸런싱 O — 커밋 못 한 구간을 다른 컨슈머가 재처리)
다음 polling 때 동일한 이벤트 재수신
~~더 있나 ??~~
→ 있음:
→ 처리가 오래 걸려 max.poll.interval.ms 초과 → 그룹에서 강제 퇴출 → 리밸런싱 → 마지막 커밋 지점부터 재처리 (실무에서 가장 흔한 중복 원인 중 하나)
→ GC pause·네트워크 단절로 하트비트 실패(session.timeout.ms) → 위와 동일하게 리밸런싱
→ auto commit(5초 주기) 사용 시 크래시 시점에 따라 커밋 안 된 처리분 통째로 재수신
→ 커밋 기록이 만료(offsets.retention.minutes, 기본 7일)된 뒤 재기동 → auto.offset.reset=earliest면 과거 레코드 재수신

## 결론 (멘탈모델 닫기)
idempotent producer는 프로듀서-브로커 구간의 중복만 해결. 브로커-컨슈머 구간까지 포함해 end-to-end로 가려면:
- 카프카 트랜잭션 (transactional.id + isolation.level=read_committed) — read-process-write 파이프라인용
- 현실적으로는 컨슈머 처리를 멱등하게 만드는 것 (키 기반 dedup, upsert 등)
