# 결제 → 정산 테이블 동기화 설계 검토 메모

> 결제 시스템의 마스터성 테이블 변경을 카프카로 받아 정산 DB에 반영하는 구조. 설계 검토 과정에서 나온 확인 사항과 대응을 정리한다.
> (사내 고유 명칭은 일반명으로 치환해 적음: `payment-service`, `merchant`, `PG_A` 등)

## 파이프라인 구조

---

> 홉이 두 개다. 문서화된 스펙은 두 번째 홉만 다룬다.

```
결제 앱 ──(홉1: 미확인)──> 결제 컨슈머 ──(홉2: 문서화됨)──> 정산 컨슈머 ──> 정산 DB
```

| 항목 | 내용 |
|---|---|
| 토픽 | `{env}.payment.master.table.sync` (마스터성 테이블). 거래 테이블 3종은 별도 토픽, 이 문서 범위 밖 |
| 파티션 키 | `{tableName}:{entityId}` |
| 발행 시점 | 결제 DB 커밋 확정 후, 롤백분 미발행 |
| 페이로드 | 결제 테이블 전체 컬럼. 필드명은 camelCase |
| DELETE | payload에 삭제 직전 상태 포함 |
| 책임 분담 | 결제는 전체 필드 그대로 발행. **선별·변환·비정규화는 정산 책임** |
| 컨슈머 규칙 | 멱등 upsert(`tableName`, `entityId`) / `occurredDateTime` 역전 방어 / 미지 필드 무시 |

메시지 구조는 대략 이런 형태다.

```json
{
  "tableName": "merchant",
  "entityId": "1001",
  "operation": "UPDATE",
  "occurredDateTime": "2026-08-06T15:30:00.123+09:00",
  "payload": { "...": "테이블 전체 컬럼" }
}
```

### 홉1의 발행 방식이 아직 미확정

문서는 정산 컨슈머가 받는 메시지(홉2)만 규정한다. 결제 앱이 CDC로 발행하는지 애플리케이션에서 직접 발행하는지는 확인되지 않았다. camelCase envelope은 결제 컨슈머가 Debezium 메시지를 변환한 결과일 수도 있고, 애초에 엔티티 기반으로 조립된 것일 수도 있다.

CDC 가설을 택하면 결제 컨슈머 홉의 존재 이유(raw CDC → 정산용 envelope 정규화)가 설명된다는 점에서 그럴듯하다.

**확인 방법**: 결제 컨슈머 앞단 토픽의 메시지를 한 건 확인한다. `before` / `after` / `source` / `op` 구조가 보이면 CDC.

**갈리는 지점**

| 항목 | 홉1이 CDC | 홉1이 앱 발행 |
|---|---|---|
| 유실 | 홉1 안전. 대신 결제 컨슈머가 새 dual-write 지점 | 홉1·홉2 양쪽에 구멍 |
| `occurredDateTime` | `source.ts_ms` 유래면 커밋 순서·단일 시계 보장 | 앱 서버 시계 → 스큐·커밋 시점 불일치 |
| 스키마 결합 | 결제 컨슈머 매핑이 수동이면 완화, 기계적 snake→camel이면 완화 없음 | 엔티티 필드명이 결합면 |

## 초기 고민에 대한 결론

---

> 처음 걱정했던 것 중 셋은 키 설계로 해소됐고, 하나가 남았다.

| 고민 | 결론 |
|---|---|
| 테이블명이 파티션 키면 파티션 수를 못 늘리는 것 아닌가 | **해소.** 키가 `{tableName}:{entityId}`라 순서 보장 단위가 "행". 파티션 수 자유 |
| 테이블 추가되면 파티션도 추가해야 하나 | **해소.** 해싱 배정이라 불필요. 테이블:파티션 1:1 고정 방식이었다면 문제였을 것 |
| 컬럼명 변경이 정산에 영향 | **조건부 완화.** payload가 엔티티 필드명 기반 + 미지 필드 무시 규칙. 단 홉1이 CDC이고 매핑이 기계적이면 완화되지 않음 |
| 행위가 아닌 데이터 단위로 사고하게 됨 | **방향 옳음.** 마스터 데이터는 테이블 sync가 맞고, 거래성 데이터는 이미 별도 토픽으로 분리돼 있음 |
| 여러 파티션의 데이터로 정산 한 테이블을 만들게 됨 | **미해소. 남은 최대 리스크** (아래 참조) |

### 파티션 키 설계에 대한 정리

순서 보장이 필요한 최소 단위는 "테이블 전체"가 아니라 "같은 행"이다. `merchant:1001`의 insert→update→delete 순서만 지켜지면 되고, `merchant:1001`과 `merchant:2002`의 상대 순서는 정산에 의미가 없다.

만약 키가 테이블명뿐이었다면 해당 테이블의 모든 변경이 영원히 파티션 1개로 몰려 처리 병렬성이 1로 고정되고, 나중에 파티션 수를 늘리는 순간 `hash % N`이 바뀌어 순서 역전이 발생했을 것이다.

## 남은 리스크

---

> 스펙에 적힌 부분은 잘 잡혀 있다. 남은 위험은 전부 스펙에 안 적힌 곳에 있다.

### 1. 유실 — 우선순위 최상

커밋은 성공했는데 발행 직전에 프로세스가 죽으면 그 변경은 정산에 영영 오지 않는다. 홉1이 CDC라도 결제 컨슈머에서 오프셋 커밋과 재발행 사이에 같은 구멍이 생긴다. **유실이 사라지는 게 아니라 위치가 옮겨갈 뿐이다.**

정산은 돈이라 조용한 유실이 가장 위험하고, 보통 몇 달 뒤 정산 오차로 발견된다.

- 홉1·홉2 중 어디서 유실이 가능한지 확인
- transactional outbox 적용 여부 확인
- 결제 DB와 정산 DB 간 건수·체크섬 대사(reconciliation) 배치는 어느 쪽이 만들든 필요

### 2. 테이블 간 순서 미보장 + 비정규화 책임

키가 `{tableName}:{entityId}`라 **같은 엔티티라도 테이블이 다르면 파티션이 다르다.**

```
merchant:1001         → hash → 파티션 3
merchant_detail:1001  → hash → 파티션 7    ← 같은 가맹점, 다른 파티션
```

파티션이 다르면 도착 순서 보장이 전혀 없다. 상세가 마스터보다 먼저 도착할 수 있다. 문서가 비정규화를 정산 책임으로 못 박았으므로 이 문제는 정산이 전부 떠안는다.

**대응** (조합해서 사용)

1. 함께 묶이는 테이블 그룹은 aggregate root 기준 키(`merchant:{merchantId}`)를 쓰도록 예외 협의 — 근본 해법
2. 순서 역전 내성 설계 — FK 제약 미사용, 테이블별 독립 upsert, 조합은 조회 시점이나 별도 배치
3. 버전 기반 stale 폐기 (아래)

### 3. `occurredDateTime` 역전 방어의 구멍 세 개

규칙 자체는 맞지만 타임스탬프 기반 버전 비교에는 함정이 있다.

**tie-break 미정의** — 밀리초 해상도라 같은 행을 1ms 안에 두 번 수정하면 값이 같아진다. "저장된 값보다 오래된 메시지는 무시" 규칙만으로는 동일할 때 처리가 미정이다. 정산 쪽에서는 일단 **같으면 나중 도착 채택**으로 잡되, 단조 증가 시퀀스를 받는 게 근본적으로 안전하다.

**"변경 발생 시각"의 정의** — 엔티티 수정 시점인지 커밋 시점인지에 따라 DB 최종 상태와 어긋날 수 있다.

```
TX1: t=100 에 row 수정 → occurredDateTime=100, 커밋은 t=200
TX2: t=150 에 같은 row 수정 → occurredDateTime=150, 커밋은 t=160

DB 최종 상태 = TX1의 값 (나중에 커밋)
정산 판단   = 150 > 100 이므로 TX2 값 유지 → 영구 불일치
```

같은 행이면 로우 락 때문에 잘 안 나오지만, 락 획득 전에 타임스탬프를 찍으면 발생한다.

**시계 소스** — 앱 서버 시각이면 인스턴스 간 클럭 스큐가 그대로 순서 오류가 된다. binlog 커밋 시각이나 DB `NOW()`처럼 단일 소스면 안전하다.

> 홉1이 CDC이고 `occurredDateTime`이 binlog 커밋 시각에서 유래한다면 두 번째·세 번째 구멍은 자동으로 닫힌다. 홉1 확인이 중요한 이유.

### 4. 엔티티 필드명 결합

payload 필드명이 결합면이다. 결제팀 입장에서는 "변수명 정리"로 인식되는 종류의 변경이라 통보 없이 나갈 확률이 오히려 높다. 필드명 변경·삭제는 breaking change라는 합의가 필요하다.

### 5. PII

전체 컬럼 발행이라 결제수단·가맹점 테이블에 민감정보(사업자번호, 정산계좌, 이메일 등)가 평문으로 실릴 수 있다. 카프카 리텐션 기간 동안 브로커에 남고, 컨슈머 그룹을 추가하면 누구나 읽을 수 있다. 마스킹·암호화 정책 확인 필요.

### 6. 결제 컨슈머 홉

변환을 담당한다면 홉의 존재가 설명되지만, 재발행 시 **키를 그대로 유지하는지**, **멀티스레드 처리로 순서가 뒤집히지 않는지** 확인이 필요하다. 여기서 깨지면 결제팀이 보장한 순서는 정산 입장에서 무의미하다.

## 정산 컨슈머 설계 결론

---

> 위 리스크에 대응해 정산 쪽에서 확정해야 할 것들.

**FK 제약을 걸지 않는다** — 순서 역전으로 참조 대상이 아직 없을 수 있다.

**soft delete 필수** — 물리 삭제하면 `occurredDateTime`이 같이 사라져, stale UPDATE가 도착했을 때 비교할 저장값이 없어 신규 데이터로 오인하고 행을 부활시킨다.

```
DELETE(t=200) 도착 → 물리 삭제
stale UPDATE(t=150) 도착 → 비교 대상 없음 → insert → 삭제된 행 부활
```

감사 추적·소급 정산도 이유지만, 역전 방어 규칙이 성립하려면 물리 삭제가 불가능하다는 게 더 직접적이다.

**`occurredDateTime`을 컬럼으로 저장하되, 소스 테이블별로 분리한다** — 비정규화로 여러 테이블을 한 행에 합칠 때 타임스탬프를 하나로 합치면 한쪽의 최신 이벤트가 다른 쪽의 stale 판정을 오염시킨다. `merchantOccurredAt`, `merchantDetailOccurredAt` 식으로 나눠 들고 있어야 한다.

**필요한 필드만 명시적으로 매핑하고, 매핑 로직은 한곳에 모은다** — 전체 payload를 통째로 DTO에 받으면 결제팀이 컬럼을 추가할 때마다 깨진다. 이 매핑 레이어가 결합면이므로, 결제팀 변경 시 여기만 보면 되게 만든다. 그리고 정산이 어떤 필드에 의존하는지 목록을 결제팀에 공유한다.

**부분 상태 저장을 허용한다** — 조합할 대상이 아직 안 왔으면 실패시키지 말고 부분 상태로 저장한 뒤 나중에 채운다.

**compaction이 켜져 있으면 백필 수단으로 활용한다** — `{tableName}:{entityId}` 키 구조는 compaction과 궁합이 좋아, 토픽 리플레이만으로 정산 DB 재구축이 가능하다. 단 DELETE를 tombstone(value=null)으로 보내면 과거 레코드가 물리적으로 사라져 "삭제됐다"는 사실까지 잃는다. 현재는 payload에 삭제 직전 상태가 담기므로 이 문제는 없다.

## 결제팀 확인 목록

---

> 우선순위 순.

**상**

1. **홉1 발행 방식** — CDC(Debezium)인가, 앱에서 직접 발행인가. 결제 컨슈머의 매핑은 수동인가 기계적 snake→camel인가
2. **유실 가능 지점** — 홉1·홉2 중 어디서 유실될 수 있는가. outbox 적용 여부. 대사 수단 유무
3. **`occurredDateTime` 정의** — 커밋 시점 기준인가. 시계 소스는 어디인가. 동일 값이 나올 수 있는가
4. **엔티티 필드명 변경 통보** — payload 필드명이 결합면이라는 합의, 정산 의존 필드 목록 공유
5. **결제 컨슈머 재발행** — 키 유지 여부, 멀티스레드 처리 시 순서 보장 여부

**중**

6. `txId` 등 트랜잭션 경계 정보 추가 가능 여부 — 비정규화 대상 테이블이 많다면 요청 가치 있음
7. 함께 묶이는 테이블 그룹에 aggregate root 키 예외 협의
8. PII 마스킹 정책
9. 파티션 수 / 리텐션 / compaction 설정 — 파티션 수는 나중에 늘리면 순서 역전이 생기므로 처음에 넉넉히
10. 초기 백필 스냅샷 제공 방식 (신규 테이블 추가, 정산 DB 재구축 시)
11. 복합키 테이블 존재 여부 — `entityId` 단일키 전제가 언제 깨지는가
12. 스키마 버전 필드 / 스키마 레지스트리 도입 여부
13. DLQ 정책과 재발행 요청 경로
