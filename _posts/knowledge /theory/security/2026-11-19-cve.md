## 1. 정의

---

> CVE(Common Vulnerabilities and Exposures)는 **공개된 보안 취약점 하나하나에 붙이는 고유 식별자**다. 이 식별자를 발급·관리하는 국제 공동 운영 체계를 CVE 프로그램(CVE Program)이라 부른다. (참고 : [CVE 프로그램 소개](https://www.cve.org/About/Overview))

* 같은 취약점을 벤더·보안 업체·스캐너가 서로 다른 이름으로 부르면 대응이 엇갈린다. CVE ID 하나로 모두가 같은 취약점을 가리키게 하는 게 목적이다.
* "CVE"는 ID 하나(`CVE-2022-22965`)를 가리키기도 하고 이 제도 전체를 가리키기도 해서, 공식 사이트는 제도 쪽을 "CVE Program"으로 구분해 부른다.

### CVE 프로그램의 구성

| 구성 요소 | 내용 |
| --- | --- |
| 운영 주체 | 미국 [MITRE](https://www.mitre.org/)가 운영하고 [CISA](https://www.cisa.gov/)(미국 사이버보안·기반시설보안청)가 후원한다 |
| [CVE Board](https://www.cve.org/ProgramOrganization/Board) | 프로그램의 방향과 정책을 정하는 위원회 |
| [CNA](https://www.cve.org/ProgramOrganization/CNAs) | CVE ID 발급 권한을 위임받은 기관 (벤더, 오픈소스 재단, GitHub 등) |
| [CNA 운영 규칙](https://www.cve.org/ResourcesSupport/AllResources/CNARules) | ID를 언제·어떻게 발급하고 레코드에 무엇을 적을지 정한 절차 |
| CVE List | 발급된 CVE 레코드를 모은 공개 목록. [cve.org](https://www.cve.org/)에서 검색한다 |

* CVE 레코드 자체는 "ID + 짧은 설명 + 참고 링크" 수준이다. 심각도 점수나 영향받는 버전 범위 같은 상세 정보는 아래 다른 체계들이 덧붙인다.

## 2. CVE ID 와 발급 주체

---

> CVE ID는 `CVE-연도-일련번호` 형식이고, CNA라 불리는 승인된 기관이 발급한다.

```
CVE-2022-22965
    │    └── 일련번호 (4자리 이상, 자릿수 제한 없음)
    └─────── ID를 예약·발급한 연도 (공개 연도와 다를 수 있음)
```

**[CNA(CVE Numbering Authority)](https://www.cve.org/ProgramOrganization/CNAs)**
- CVE ID를 발급할 권한을 받은 기관.
  - 대형 벤더(Microsoft, Google, Red Hat 등), 오픈소스 재단, GitHub 등이 CNA다.
  - 전체 목록은 [CVE 파트너 목록](https://www.cve.org/PartnerInformation/ListofPartners)에서 볼 수 있다.
  - Spring 프로젝트의 CVE는 VMware(현 Broadcom) 쪽에서 발급하고, [Spring 보안 공지](https://spring.io/security) 페이지에 정리된다.
* 취약점을 발견하면 보통 해당 벤더에 비공개로 제보 → 패치 준비 → CVE ID 예약 → 패치 배포와 함께 공개 순으로 진행된다.
* 공개 전에는 ID만 예약(RESERVED)된 상태로 존재할 수 있다.

## 3. CVE 와 함께 보는 체계

---

> CVE는 이름표이고, 얼마나 위험한지(CVSS), 어떤 종류의 결함인지(CWE), 어떤 버전이 영향받는지(NVD·GHSA·OSV)는 각각 다른 체계가 담당한다.

| 이름 | 역할                                                                                                       | 예 |
| --- |----------------------------------------------------------------------------------------------------------| --- |
| CVE | 취약점 식별자                                                                                                  | `CVE-2022-22965` |
| [CVSS](https://www.first.org/cvss/) | 심각도 점수(0.0~10.0)와 근거 벡터                                                                                  | `9.8 CRITICAL` |
| [CWE](https://cwe.mitre.org/) | 결함 유형 분류                                                                                                 | `CWE-94` 코드 인젝션 |
| [NVD](https://nvd.nist.gov/) | 미국 [NIST](https://www.nist.gov/)가 CVE에 CVSS·CWE·영향 제품([CPE](https://nvd.nist.gov/products/cpe))을 붙여 둔 DB | |
| [GHSA](https://github.com/advisories) | GitHub Advisory Database의 ID. <br> 패키지 이름·버전 범위가 정리돼 있음                                                  | `GHSA-36p3-wjmg-h94x` |
| [OSV](https://osv.dev/) | 여러 생태계(Maven, npm, PyPI 등)의 취약점을 패키지·버전 기준으로 모은 DB와 API                                                  | |

- GHSA나 OSV는 CVE와 별도 ID를 쓰지만 `aliases`로 CVE ID를 연결해 둔다.
- CVE가 아직 없는 취약점은 GHSA ID만 있을 수도 있다.

### CVSS 벡터 읽기

CVSS 점수는 숫자만 보지 말고 벡터를 함께 본다. 벡터에 "어떤 조건에서 공격 가능한가"가 들어 있다. CVSS v3.1 기본 지표는 다음과 같다.

| 지표 | 의미 | 값 |
| --- | --- | --- |
| `AV` (Attack Vector) | 어디서 공격하나 | `N` 네트워크 / `A` 인접망 / `L` 로컬 / `P` 물리 |
| `AC` (Attack Complexity) | 공격 조건이 까다로운가 | `L` 낮음 / `H` 높음 |
| `PR` (Privileges Required) | 공격자에게 필요한 권한 | `N` 없음 / `L` 낮음 / `H` 높음 |
| `UI` (User Interaction) | 피해자의 행동이 필요한가 | `N` 불필요 / `R` 필요 |
| `S` (Scope) | 취약한 컴포넌트 밖까지 영향이 번지나 | `U` 그대로 / `C` 변경 |
| `C` / `I` / `A` | 기밀성 / 무결성 / 가용성 피해 | `N` 없음 / `L` 낮음 / `H` 높음 |

`AV:N/AC:L/PR:N/UI:N`이면 "인터넷 어디서든, 별다른 조건 없이, 로그인 없이, 사용자 클릭 없이" 공격 가능하다는 뜻이라 대응 우선순위가 가장 높다.

## 4. 예시 : CVE-2022-22965 (Spring4Shell)

---

> 2022년 3월 공개된 Spring Framework 원격 코드 실행 취약점으로, CVE 하나를 읽을 때 봐야 할 항목이 모두 들어 있다.

OSV API(`https://api.osv.dev/v1/vulns/CVE-2022-22965`)로 조회한 값이다.

| 항목 | 값 |
| --- | --- |
| 별칭 | `GHSA-36p3-wjmg-h94x` |
| 심각도 | CRITICAL, `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` |
| CWE | `CWE-74`, `CWE-94` |
| 영향 패키지 | `spring-beans`, `spring-webmvc`, `spring-webflux` 5.3.0 이상 5.3.18 미만, 5.2.20 미만 |
| 영향 Boot 스타터 | `spring-boot-starter-web`·`-webflux` 2.6.0 이상 2.6.6 미만, 2.5.12 미만 |

설명 본문(번역)은 이렇다.

> JDK 9 이상에서 동작하는 Spring MVC 또는 Spring WebFlux 애플리케이션은 데이터 바인딩을 통한 원격 코드 실행에 취약할 수 있다. 알려진 공격은 애플리케이션이 Tomcat에 WAR로 배포된 경우에 동작한다. 기본값인 Spring Boot 실행 가능 jar로 배포했다면 이 공격에는 취약하지 않다. 다만 취약점 자체는 더 일반적인 성격이라 다른 공격 방법이 있을 수 있다.

CVE 하나에서 읽어 낼 것은 이렇게 정리된다.

* **영향 버전** : 내가 쓰는 라이브러리 버전이 범위 안인가. 직접 의존성이 아니라 Boot 스타터를 통해 들어온 전이 의존성도 포함이다.
* **공격 조건** : JDK 9+, Tomcat WAR 배포처럼 설명에 붙은 전제 조건. 조건에 안 맞으면 당장 위험도는 낮지만, 설명대로 "다른 공격 방법이 있을 수 있다"는 단서가 붙으면 업그레이드는 한다.
* **수정 버전** : `fixed`로 표기된 첫 버전 이상으로 올린다.
* **우회책(workaround)** : 바로 업그레이드할 수 없을 때 벤더가 제시하는 임시 조치. 이 취약점은 `@InitBinder`로 바인딩 허용 필드를 제한하는 방법이 안내됐다.

## 5. 내 프로젝트 의존성 점검

---

> 의존성 목록을 뽑아 취약점 DB에 버전을 조회하면 된다. 스캐너 도구들도 결국 이 과정을 자동화한 것이다.

실무에서는 아래 자동화 도구를 쓰지만, 이 절에서는 도구가 안에서 하는 두 단계를 직접 돌려 봤다. Spring Boot 2.6.4와 3.5.4 프로젝트(`spring-boot-starter-web` 하나만 의존)를 Maven으로 만들어 조회했다. (조회일 2026-11-19, 결과는 DB가 갱신되면 달라진다)

### 취약점 DB

"이 패키지의 이 버전 범위에 이런 취약점이 있다"를 모아 둔 데이터베이스다. CVE 레코드에는 패키지 버전 범위가 없으므로 이런 DB를 조회한다.

| DB | 운영 | 쓰는 도구 |
| --- | --- | --- |
| NVD | 미국 NIST | OWASP Dependency-Check |
| GitHub Advisory Database | GitHub | Dependabot |
| OSV | Google 주도, GitHub Advisory 등 여러 출처를 모아 패키지·버전 조회 API 제공 | OSV-Scanner |

여기서는 가입이나 API 키 없이 쓸 수 있는 OSV를 썼다.

### 1단계 : 의존성 목록 뽑기

`pom.xml`에는 스타터 하나만 적었지만 전이 의존성까지 실제로 들어오는 라이브러리는 32개다. `dependency:list`가 이 전체를 버전까지 확정해 파일로 남긴다. `-DincludeScope=runtime`은 테스트 전용 라이브러리를 빼고 실행 시 올라가는 것만 남긴다.

```bash
mvn dependency:list -DoutputFile=deps.txt -DincludeScope=runtime
```

```
The following files have been resolved:
   org.springframework.boot:spring-boot-starter-web:jar:2.6.4:compile
   org.springframework.boot:spring-boot:jar:2.6.4:compile
   org.springframework:spring-beans:jar:5.3.16:compile
   ...
```

각 줄은 `groupId:artifactId:jar:version:scope` 형식이다.

### 2단계 : 버전마다 취약점 DB 조회

OSV는 패키지 이름과 버전을 주면 해당하는 취약점 ID를 돌려준다.

```bash
curl https://api.osv.dev/v1/query -d '{
  "package": {"ecosystem": "Maven", "name": "org.springframework:spring-beans"},
  "version": "5.3.16"
}'
```

의존성마다 한 번씩 부르는 대신 여러 개를 한 번에 묻는 `/v1/querybatch`를 쓰면 결과가 보낸 순서대로 돌아온다. 두 개를 넣었을 때의 응답이다.

```
요청: spring-beans 5.3.16, slf4j-api 1.7.36
응답: {"results":[
        {"vulns":[{"id":"GHSA-36p3-wjmg-h94x"}, {"id":"GHSA-hh26-6xwr-ggv7"}]},  ← spring-beans
        {}                                                                    ← slf4j-api : 없음
      ]}
```

아래 스크립트는 `deps.txt`에서 패키지 이름과 버전을 꺼내 `querybatch` 한 번으로 보내고, 취약점이 조회된 의존성만 출력한다. 응답에는 ID만 오므로 심각도·수정 버전은 4절처럼 `/v1/vulns/{id}`로 따로 조회한다.

<details markdown="1">
<summary><span>OSV 일괄 조회 스크립트</span></summary>

```python
import json, sys, re, urllib.request

deps = []
for line in open(sys.argv[1]):
    m = re.match(r'\s*([^:\s]+):([^:]+):jar:([^:]+):', line)  # group:artifact:jar:version:scope
    if m:
        deps.append((m[1] + ":" + m[2], m[3]))

query = {"queries": [{"package": {"ecosystem": "Maven", "name": n}, "version": v} for n, v in deps]}
req = urllib.request.Request("https://api.osv.dev/v1/querybatch",
                             json.dumps(query).encode(), {"Content-Type": "application/json"})
result = json.load(urllib.request.urlopen(req))

total = 0
for (name, version), res in zip(deps, result["results"]):
    ids = [v["id"] for v in res.get("vulns", [])]
    if ids:
        total += len(ids)
        print(f"{name}:{version}  {len(ids)}")
print("deps", len(deps), "vulns", total)
```

</details>

### 결과

| | Boot 2.6.4 | Boot 3.5.4 |
| --- | --- | --- |
| 런타임 의존성 수 | 32 | 34 |
| 취약점이 조회된 의존성 | 17 | 11 |
| 조회된 취약점(ID) 합계 | 122 | 66 |
| 가장 많은 의존성 | `tomcat-embed-core:9.0.58` (45) | `tomcat-embed-core:10.1.43` (23) |

* Boot 2.6.4의 `spring-beans:5.3.16`에서는 위 CVE-2022-22965(`GHSA-36p3-wjmg-h94x`)가 그대로 조회된다.
* 3.5.4도 2025년 7월 릴리스라 그 뒤에 공개된 취약점이 쌓여 있다. "최신 메이저 버전을 쓰니 괜찮다"가 아니라 패치 버전까지 따라가야 한다.
* 개수에는 같은 취약점이 여러 패키지(`spring-webmvc`, `spring-beans` 등)에 중복으로 잡힌 것이 포함된다.
* 실제 판단은 개수보다 4절처럼 각 항목의 심각도와 공격 조건을 본다.

### 자동화 도구

> 매번 스크립트를 돌리지 않고 빌드·CI에 붙이는 도구들이 있다.

| 도구 | 특징 |
| --- | --- |
| [OWASP Dependency-Check](https://owasp.org/www-project-dependency-check/) | Maven·Gradle 플러그인. NVD 데이터 기반 |
| [OSV-Scanner](https://google.github.io/osv-scanner/) | OSV DB 기반 CLI. lockfile·SBOM 스캔 |
| [Trivy](https://trivy.dev/) | 컨테이너 이미지·파일시스템·의존성 스캔 |
| [GitHub Dependabot](https://docs.github.com/en/code-security/dependabot) | GHSA 기반 알림과 버전 업 PR 자동 생성 |

## 6. CVE 가 다루지 않는 것

---

> CVE는 라이브러리·제품의 취약점을 다룬다. 내가 작성한 애플리케이션 코드의 결함은 스캐너에 잡히지 않는다.

* 의존성 스캔 결과가 깨끗해도 애플리케이션 코드에 인가 누락, 경로 검사 실수 같은 결함은 남을 수 있다.
